# qq-workflow

독립 결과 하나를 계획서 하나와 DELTA별 독립 리뷰로 처리한다. 계획서는 전체 목표·범위·완료 조건의 계약이다. `DELTA-NN.md`는 실행 단위의 구현·검증·리뷰 계약이다. 모든 작업은 `DELTA-01.md` 하나로 시작한다. 구현 중 크기 때문에 나눠야 하면 "DELTA 추가"에 따라 최대 3개까지 둔다. LEG는 만들지 않는다. 진입 기준은 `AGENTS.md`의 "작업 실행"을 따른다. 공통 실행 계약은 `docs/agents/workflow-shared.md`를 따른다.

## 적용 크기

- 크기는 DELTA 하나의 변경 diff 기준이다. 목표는 추가·삭제 합계 1,000줄 이하, 상한은 2,000줄이다. `git diff HEAD --shortstat`의 추가+삭제에 untracked 신규 파일의 줄 수(`wc -l`)를 더한다. 테스트를 포함한다. 생성 파일과 `pnpm-lock.yaml`은 제외한다.
- 줄 수는 보조 지표다. 상한 이하여도 여러 독립 결과나 순서가 있는 여러 단계가 필요하면 `qq`를 선택하지 않는다.
- 계획 단계에서 DELTA 하나로 상한을 넘을 것으로 예상되면 승인 전에 보고한다.
- 구현 중 상한을 넘으면 "DELTA 추가"를 따른다.

## DELTA 추가

qq의 DELTA는 같은 결과를 크기 때문에 나눈 실행 단위다. DELTA를 추가해도 계획서의 목적·범위·완료 조건·확정 정책은 바꾸지 않는다.

- 구현 중 현재 DELTA가 상한을 넘으면 사용자에게 묻지 않고 DELTA를 추가한다.
- 한 작업의 DELTA는 `DELTA-01`을 포함해 최대 3개다.

다음 경우에는 중단하고 원인과 전환안을 보고한다. 사용자 결정 없이 `rubber-workflow`로 전환하지 않는다.

- DELTA 3개 안에서 각 DELTA를 상한 이하로 나눌 수 없다.
- 독립 결과가 여러 개로 늘어난다.
- 목표·범위·완료 조건이나 확정 정책을 바꿔야 한다.

중단할 때 커밋한 DELTA는 작업 브랜치에 남기고 `dev`에 통합하지 않는다. 미커밋 변경은 작업 트리에 보존한다. 보고에는 완료한 DELTA, 남은 작업과 미커밋 변경 위치를 적는다.

추가 절차:

1. `dev`에서 직접 구현 중이었으면 `dev`에서 작업 브랜치를 만들어 이동한다. 중간 DELTA 커밋이 `dev`에 먼저 들어가지 않게 하기 위해서다.
2. 현재 DELTA 파일의 대상 파일과 담당 완료 조건을 줄인다. 넘긴 범위로 다음 번호의 DELTA 파일을 만들고 추가 이유를 적는다.
3. 계획서의 `DELTA 목록`을 갱신한다. 계획서의 모든 완료 조건은 한 DELTA에 배정한다.
4. 현재 DELTA에 속하지 않는 변경은 `git stash` 또는 작업 폴더의 patch 파일로 분리한다. 한 DELTA의 검증·리뷰 범위에 다른 DELTA 변경을 섞지 않는다.

## 진행과 승인

```text
qq-workflow로 진행: 작업 설명
qq-workflow 단계-3 진행: 작업 폴더 경로
```

- 단계-1 계획 승인 뒤 단계-4까지 자동 진행한다. 이미 승인된 계획의 실행 지시는 승인으로 본다.
- 계획 승인 후 작업을 완료하면 `docs/agents/workflow-shared.md`의 "커밋과 자동 dev 통합"에 따라 로컬 커밋과 `dev` 통합까지 자동 진행한다.
- 명시적으로 한 단계만 요청하면 해당 단계까지만 진행한다.
- 파일 존재만으로 승인·검증·리뷰 통과를 추정하지 않는다. 선행 단계의 상태와 증거를 확인한다.
- 계획에 없는 구현 세부사항은 관련 지침과 확정 계약으로 판단한다. 목표·범위·완료 조건 또는 API·스키마·인증·암호 형식·외부 연동 정책을 바꾸는 결정은 사용자에게 확인하고 계획서의 `결정`에 기록한다.

## 작업 계약

폴더 구조와 명명은 `_works/README.md`를 따른다. 템플릿은 다음과 같다.

| 문서   | 템플릿                 | 파일명                  |
| ------ | ---------------------- | ----------------------- |
| 계획서 | `qq-01-계획.md`        | `01-계획.md`            |
| DELTA  | `qq-DELTA-NN.md`       | `DELTA-01.md`           |
| 리뷰   | `qq-IMPL-REVIEW-NN.md` | `DELTA-01-REVIEW-01.md` |

`_meta.md`에는 다음을 기록한다.

- 워크플로우: qq
- 상태: 계획 / 승인 / 구현 / 리뷰 / 커밋 대기 / 완료 / 중단
- 작업 브랜치와 착수 `HEAD` 전체 SHA
- 관련 RQ와 GitHub 이슈(없으면 없음)
- 계획 승인 근거와 실행 범위
- 현재 DELTA 번호
- DELTA별 최신 리뷰 파일명과 커밋 SHA(해당 단계 완료 시)

계획서에는 목적, 변경 대상, 확정 정책·계약, 완료 조건, 최종 검증, 범위 밖, 참고 문서, 관련 함정, 결정, DELTA 목록을 적는다. API·스키마·봉투 형식 변경은 해당 계약과 실패 조건을 리뷰할 수 있게 명시한다. RQ 진행 상태·수용 조건 체크 갱신이 필요하면 완료 조건에 넣는다. 테스트 내부 구조나 구현 코드까지 미리 작성하지 않는다.

`DELTA-NN.md`에는 목적, 기준 커밋, 대상 파일, 담당 완료 조건, 관련 검증 명령, 최종 검증 대상(누적), 최종 검증 예정 항목, 구현·검증 결과, 리뷰 인계와 커밋 SHA를 적는다. 담당 완료 조건은 계획서의 조건을 그대로 옮긴다.

## 단계-1. 계획

1. `workflow-shared.md`의 "착수와 변경 범위"를 확인한다.
2. 변경 대상과 완료 조건을 정할 만큼 관련 코드와 `CONTEXT-MAP.md`에서 찾은 RQ·ADR을 읽는다. 관련 GitHub 이슈를 확인한다.
3. 작업 폴더와 `_meta.md`, `01-계획.md`, `DELTA-01.md`를 작성한다. `DELTA-01`에 모든 완료 조건을 배정한다. 필요한 검증을 `verification.md`에 따라 실행 가능한 명령으로 지정한다.
4. 계획서와 `DELTA-01.md`를 제시하고 승인을 받는다. 승인 전에 구현하지 않는다.
5. `dev` 또는 이번 작업용으로 `dev`에서 만든 브랜치에서 구현한다. 다른 작업 브랜치이면 임의로 전환하지 않고 보고한다.

## 단계-2. DELTA 구현·검증

현재 DELTA마다 수행한다.

1. 계획서, 현재 DELTA, 참고 문서와 관련 함정을 읽고 현재 DELTA 범위를 구현한다.
2. `docs/agents/testing.md`를 읽고 보호할 위험과 기존 검증을 확인한다. 필요한 테스트만 작성하고 TDD 적용 여부를 결정한다. 문서만 바꾸는 작업에는 구현을 복제하는 테스트를 만들지 않는다.
3. 현재 DELTA의 대상 검증을 `verification.md`에 따라 실행하고 DELTA 파일에 기록한다. 통합 검증이 필요하면 DELTA 파일의 "최종 검증 대상(누적)"에 쌓고 `미실행(최종 검증 예정)`으로 기록한다. DELTA 커밋에는 그 DELTA의 대상 검증 결과가 있어야 한다.
4. 필요한 장기 정책·계약 문서를 같은 DELTA에서 갱신한다. RQ 진행 상태, ADR "구현 중 확정" 절, `docs/operations/` 문서가 대상이다. 갱신 조건은 `AGENTS.md`의 "문서와 요구사항 갱신"이다. 범위 밖 결함은 `workflow-shared.md`의 "문서와 최종 보고"에 따라 처리한다. 이 과정에서 바꾼 추적 파일도 해당 DELTA의 검증·리뷰 범위에 포함한다.
5. 마지막에 `workflow-shared.md`의 "테스트 정리"를 하고 결과를 DELTA 파일에 기록한다.
6. 리뷰 통과 전에는 커밋하지 않는다. 현재 DELTA 변경을 작업 트리에 남기고 독립 리뷰에 넘긴다.

## 단계-3. DELTA 독립 리뷰·수정

구현자와 다른 읽기 전용 에이전트 또는 새 세션이 수행한다. 별도 단계 실행 시에도 이전 대화 없이 리뷰할 수 있어야 한다. 독립 리뷰 수단이 없으면 커밋하지 않고 인계 자료를 남긴다. 구현자 자체 점검을 독립 리뷰 통과로 기록하지 않는다.

리뷰 범위 고정, 공통 인계 자료는 `workflow-shared.md`의 "착수와 변경 범위", "리뷰 기록"을, 증거 구분은 `verification.md`를 따른다. 추가로 계획서, 현재 DELTA 파일, 확정 결정, 기존 변경의 제외 목록, 이전 finding 상태를 전달한다. 리뷰 대상은 현재 DELTA의 기준 커밋 이후 변경과 담당 완료 조건이다.

리뷰 파일 하나에 두 결과를 구분해 기록한다. 한 독립 리뷰어가 둘 다 수행하거나 서로 다른 리뷰어에게 나눌 수 있다.

- Spec: 계획서·현재 DELTA·확정 결정·관련 RQ·ADR·구현·검증 증거를 대조한다.
  - 담당 완료 조건별로 `PASS` / `FAIL` / `미확인`과 근거를 기록한다.
- Standards: `AGENTS.md`·참고 문서·`docs/agents/writing-styles.md`·`docs/agents/testing.md`와 변경 코드를 대조한다.
  - 지침 위반·기능 결함·회귀·검증 누락·시크릿 노출(RQ-027)을 위치와 근거로 기록한다.

finding과 처리 규칙:

- ID·상태·재리뷰 기록은 `workflow-shared.md`의 "리뷰 기록"을 따른다. finding 번호는 DELTA마다 새로 매긴다. 심각도는 같은 절(`workflow-shared.md`의 "리뷰 기록")의 정의를 따른다.
- `FAIL`·`미확인`과 미해결 blocker·major는 커밋을 막는다. blocker·major를 후속 작업으로 미뤄 통과시키지 않는다. minor는 수정하거나 남기는 이유를 기록한다.
- 구현자가 결함을 수정하고 관련 검증을 실행한다. 기능 수정의 테스트 작성은 `docs/agents/testing.md`를 따르고, 수정으로 테스트를 더하거나 고쳤으면 `workflow-shared.md`의 "테스트 정리"를 다시 한다. 기존 테스트를 제거하거나 약화하면 보호하던 계약과 대체 검증을 리뷰 입력에 포함한다.
- 재리뷰는 수정 영역, 영향받은 완료 조건과 이전 미해결 finding을 대상으로 한다. 범위가 바뀌면 현재 DELTA 전체 변경을 다시 리뷰한다.
- 리뷰·수정은 DELTA마다 최대 3라운드다. 세 번째 리뷰에서도 차단 항목이 남으면 커밋하지 않고 남은 항목과 다음 조치를 보고한다.

## 단계-4. DELTA 커밋·마무리

1. 현재 DELTA 최신 리뷰의 담당 완료 조건이 모두 `PASS`이고 미해결 blocker·major가 없는지 확인한다. 리뷰가 없거나 대상 소스가 달라졌으면 커밋하지 않는다.
2. 마지막이 아닌 DELTA는 단계-2의 대상 검증 결과를 확인한다. 마지막 DELTA는 대상 검증 결과를 확인하고, 계획서의 최종 검증을 마친 뒤 작업 완료와 `dev` 통합으로 넘어간다. 최종 검증은 `verification.md`의 "커밋과 완료"에 따라 마지막 DELTA 커밋 전이나 커밋 뒤 통합 전에 한 번 실행한다. 같은 입력에서 이미 실행한 결과의 재사용 여부는 `verification.md`의 "결과 재사용"을 따른다.
3. `workflow-shared.md`의 "커밋과 자동 dev 통합"에 따라 staged 범위를 확인한다.
4. 현재 DELTA를 로컬 커밋한다. 커밋 SHA를 DELTA 파일과 `_meta.md`에 기록한다.
5. 남은 DELTA가 있으면 커밋한 SHA를 다음 DELTA의 기준 커밋으로 적고 단계-2로 돌아간다.
6. 마지막 DELTA를 커밋했고 필요한 최종 검증을 마쳤으면 `workflow-shared.md`의 "커밋과 자동 dev 통합"에 따라 로컬 `dev` 통합을 마친다. DELTA 커밋은 재그룹화하지 않고 그대로 통합한다. 통합 결과를 `_meta.md`에 기록한다.
7. 추가 코드·문서 변경이 필요하면 해당 DELTA의 단계-2와 단계-3으로 돌아간다. 이미 커밋한 변경의 수정은 새 커밋으로 남긴다. 마무리 기록만으로 리뷰 이후 변경을 완료 처리하지 않는다.
8. `_meta.md`를 완료로 바꾸고 작업 폴더를 `_works/README.md`에 따라 보관한다. 완료한 DELTA, 새 실행·재사용·미실행 검증과 실패 수, 남은 위험, 커밋 SHA와 push 미실행을 보고한다.

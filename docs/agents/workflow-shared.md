# workflow-shared

`qq-workflow`와 `rubber-workflow`의 공통 실행 계약이다. 방식 선택 기준은 `AGENTS.md`의 "작업 실행"이 소유한다. 단계, 계획 승인 시점, 커밋 단위·시점, 리뷰 횟수와 산출물 형식은 각 workflow 문서가 소유한다. 리뷰 심각도는 이 문서의 "리뷰 기록"이 정한다. 직접 작업도 이 문서를 따른다. 단 "리뷰 기록"은 적용하지 않고, 계획·실행 단위 문서에 적을 내용은 대화에 기록한다.

## 진입과 작업 계약

- `AGENTS.md`, 이 문서, 선택한 workflow 문서와 `_works/README.md`를 읽는다.
- 설계 기준은 `CONTEXT-MAP.md`에서 작업할 모듈의 근거 RQ·ADR을 찾는다. 현재 변경에 직접 적용되는 `docs/requirements/mail-sending.md`의 RQ, `docs/adr/`의 결정, `docs/api/`·`docs/operations/` 문서만 추가로 읽는다. 읽는 규칙은 `docs/agents/domain.md`다.
- 이전 대화 없이 현재 계획 또는 실행 단위 문서로 목적, 범위, 확정 계약, 완료 조건과 검증 방법을 이해할 수 있어야 한다. `qq`는 계획서와 현재 DELTA, `rubber`는 `checklist.md`, 현재 `LEG-NN.md`(LEG를 쓰는 작업)와 현재 DELTA에 실행 계약을 적는다.
- 특정 단계만 요청받으면 해당 단계에서 종료한다. 목표·포함 범위·완료 조건이나 확정 정책을 바꾸는 결정은 사용자에게 확인한다. 이미 승인된 실행 범위 안의 구현 세부사항은 관련 지침으로 판단한다.
- 구현이 RQ·ADR과 충돌하면 `AGENTS.md`의 "문서와 요구사항 갱신"을 따른다. 충돌을 발견한 실행 단위에서 처리 방식을 확인하고 마지막 단위로 미루지 않는다.

## 착수와 변경 범위

- 현재 브랜치, `HEAD`, tracked·untracked 변경과 해당 작업의 무시 파일을 확인한다. 기존 변경을 보존하고 이번 작업 범위와 구분한다.
- `dev` 또는 `dev`에서 만든 이번 작업 브랜치를 사용한다. workflow가 작업 브랜치를 요구하면 그 규칙을 따른다. 워크트리는 기본으로 쓰지 않는다. 다른 브랜치가 체크아웃된 공유 체크아웃을 보호해야 하거나 병렬 에이전트가 같은 작업 트리를 쓰면 안 될 때만 `dev`에서 분기한 별도 `git worktree`를 쓴다.
- 작업 브랜치 이름은 `<커밋 타입>/<작업 slug>`를 쓴다. 예: `docs/agent-workflow`.
- 작업 문서에 기록된 브랜치와 다르면 임의로 전환하지 않고 보고한다. 안전하게 브랜치를 전환할 수 없는 변경이 있으면 보존 방법을 확정하기 전까지 전환하지 않는다.
- 실행 단위의 기준 커밋과 대상 파일을 기록한다. 한 단위에 다른 단위의 변경을 섞지 않는다.
- 커밋 전 변경은 `git diff HEAD -- <대상 경로>`와 `git status --short`로 확인한다. 커밋된 변경은 실행 단위의 기준 커밋과 대상 커밋 사이의 diff로 확인한다.
- `git diff`에 나오지 않는 untracked 파일은 목록과 전문을 함께 확인한다. 리뷰어에게도 전달한다.

## 검증

검증 단계, 범위 선택, 결과 재사용, 여러 에이전트의 검증 분담, 증거 기록은 [verification.md](verification.md)가 정한다.

## 테스트 정리

모든 workflow가 DELTA 구현을 마친 뒤, 리뷰에 넘기기 전에 한다. 기준은 [testing.md](testing.md#완료-전-정리)다. 이 절은 시점, 대상, 기록만 정한다.

- 시점: DELTA 구현 단계의 마지막이다. 리뷰 수정으로 테스트를 더하거나 고쳤으면 그 수정 뒤에도 한 번 한다.
- 대상: 이번 DELTA가 새로 추가한 테스트만이다. 이전부터 있던 테스트는 `testing.md`의 "기존 테스트 보호"를 따른다.
- 하는 일: 중복, 탐색용, 구현 세부사항에만 종속된 테스트를 통합하거나 지운다. 다른 파일이 이미 보는 규칙의 반복 케이스도 지운다.
- 실행: 정리한 spec 파일만 경로 패턴으로 1회 돌린다. L0 전체를 돌리지 않는다. 재사용 여부는 `verification.md`의 "결과 재사용"을 따른다.
- 기록: 지우거나 합친 테스트마다 보호하던 계약과 대체 검증을 한 줄로 남긴다. 위치는 qq가 DELTA 파일의 "구현·검증 결과", rubber가 DELTA 파일 `결과`의 `테스트 정리` 항목이다. 정리할 것이 없으면 "정리 대상 없음"과 확인한 파일을 적는다.
- 독립 리뷰어는 중복·약한 단언 후보를 minor finding으로 짚는다. 리뷰어가 직접 지우지 않는다.

## 리뷰 기록

리뷰 단계와 독립 리뷰 필요 여부, 리뷰 기록 위치, 종료 기준과 라운드 상한은 각 workflow 문서를 따른다.

- 독립 리뷰는 구현자와 다른 읽기 전용 에이전트 또는 새 세션에서 수행한다. 구현자의 자체 점검을 독립 리뷰 통과로 기록하지 않는다.
- 리뷰 범위는 기준 커밋부터 리뷰 시점 `HEAD`까지(커밋 전이면 작업 트리 변경)로 못박아 전달한다. 범위 없이 부르면 리뷰어가 `main`과의 전체 diff부터 시도하다 범위를 좁히는 데 도구 호출을 쓴다.
- 리뷰 입력에 기준 커밋·대상 diff·파일 목록, 현재 실행 계약과 관련 지침, 관련 RQ·ADR, 관련 함정, 검증 증거와 미실행 항목을 포함한다.
- 리뷰 범위를 고정한 뒤 구현자는 리뷰 대상 범위의 파일을 동시에 수정하지 않는다. finding에는 파일 위치, 문제, 계약·지침 근거와 필요한 조치를 적는다.
- 필수 완료 조건, 검증 또는 해당 workflow의 리뷰 게이트가 미충족이면 완료 처리하지 않는다.
- 심각도는 세 가지다. `blocker`: 잘못된 계약·데이터 손실·중복 발송·보안·시크릿 노출(RQ-027)·사용자 결정 필요. `major`: 기능 결함·회귀·필수 검증 누락. `minor`: 이름·문구·스타일.

리뷰 파일을 남기는 workflow는 다음도 따른다.

- finding ID는 `F-R<라운드>-<일련번호>` 형식이다. 예: `F-R01-03`.
- 상태는 `[open]`, `[resolved]`, `[rejected]`, `[deferred]`다. 수정 위치·검증 근거, 기각 근거 또는 처리 시점·GitHub 이슈 번호(등록 전이면 `pending-issues/`의 초안 파일명)를 기록한다.
- 재리뷰는 다음 번호의 파일에 이전 finding 상태와 새 판정을 기록한다. 이전 리뷰 파일을 덮어쓰지 않는다. 이미 해결한 영역이 다시 바뀌지 않았다면 같은 문제를 재진단하지 않는다.
- 리뷰 원문은 다음 라운드의 상태 확인에 사용한다. 완료 문서나 실행 단위의 필수 읽기 문서에 복사하지 않는다.

## 커밋과 자동 dev 통합

- 전체 작업의 완료 조건, 필요한 최종 검증(`verification.md`)과 해당 workflow의 리뷰를 충족하면 에이전트가 로컬 커밋과 `dev` 통합까지 자동으로 진행한다. 별도 커밋·병합 승인을 다시 요청하지 않는다.
- 특정 단계만 요청한 작업, 사용자 지시로 커밋·병합을 제외한 작업과 미완료 작업에는 자동 통합을 적용하지 않는다. 개별 DELTA 완료만으로 전체 작업을 병합하지 않는다.
- 커밋 시점·단위와 통합 전 커밋 정리는 각 workflow 문서를 따른다. 이번 작업 파일만 경로를 지정해 stage하고 staged diff가 검증·리뷰 범위와 일치하는지 확인한다. 커밋 전에 `git diff --cached --check`를 실행한다.
- 작업 폴더를 강제로 stage하지 않는다. 추적 대상은 `.gitignore`를 따른다.
- 작업 브랜치에서는 이번 작업 범위의 커밋만 `dev`에 병합한다. 다른 작업의 커밋이 섞였으면 임의로 포함하지 않고 범위 확인을 요청한다. 기존 작업 트리 변경은 보존한다.
- 병합은 `git merge --ff-only`로 한다. merge commit은 만들지 않는다.
- `dev`가 분기 시점에서 앞서 나갔으면 작업 브랜치를 로컬 `dev` 기준으로 rebase한다. 충돌이나 코드 변경이 생기면 해결한 결과에 필요한 검증·리뷰를 마친 뒤 병합한다.
- 병합 뒤 `dev`의 HEAD와 작업 브랜치 HEAD가 같은지 확인한다. 다른 작업의 변경이 남지 않았는지 확인하고 로컬 작업 브랜치를 `git branch -d`로 삭제한다. 별도 워크트리를 썼으면 병합 확인 뒤 `git worktree remove <경로>`로 먼저 지우고 브랜치를 삭제한다. `dev`에서 직접 작업했으면 로컬 커밋으로 통합을 마친다.
- 타인의 변경이 있거나 안전하게 통합할 수 없으면 멈추고 상태를 보고한다.
- `git rebase -i`, `git reset --hard`, 광범위한 `git clean`, force push는 사용하지 않는다.
- push, PR, 태그(`vX.Y.Z`는 GHCR 발행을 일으킨다), `dev`→`main` 병합, 운영 DB 작업은 각각 별도 사용자 요청이 필요하다.

## 문서와 최종 보고

- 작업 폴더 명명·템플릿·추적 범위·완료 폴더 보관은 `_works/README.md`를 따른다.
- 장기 지식은 기존 기준 문서로 정리한다. 요구사항 진행 상태와 수용 조건 체크는 `docs/requirements/mail-sending.md`, 결정은 `docs/adr/`, 운영 절차는 `docs/operations/`에 둔다. 작업 폴더를 영구 참조로 사용하지 않는다. 문장·참조 표기는 `docs/agents/writing-styles.md`를 따른다.
- 범위 밖 결함과 후속 작업은 `docs/agents/issue-tracker.md`의 "등록 기준"으로 분류한다. 이슈 쓰기는 같은 문서의 "게시 승인"에 따라 사용자 지시가 있을 때만 한다. 지시가 없으면 초안을 작업 폴더 `pending-issues/`에 남기고 최종 보고에서 등록을 제안한다.
- 작업이 지시받은 이슈를 완료하면 `issue-tracker.md`의 "작업 완료와 자동 종료"에 따라 닫는다. 반복될 조건과 오해하기 쉬운 신호가 있는 함정만 장기 문서(`AGENTS.md`, `docs/operations/troubleshooting.md` 등)로 승격한다.
- 최종 보고에는 완료한 실행 단위, 새 실행·재사용·미실행 검증과 실패 수, 남은 이슈·위험, 완료 커밋과 `dev` 통합 결과를 구분한다. 자동 검증과 수행하지 않은 L3·실제 SMTP·운영 검증을 구분한다. push 실행 여부를 명시한다.

# rubber-workflow

저장소 변경을 목표와 검증이 있는 작은 단위로 실행한다. 여러 단계가 필요한 작업은 DELTA로 나누고, DELTA가 많은 작업은 DELTA를 LEG로 묶는다. 이 절차는 RQ 구현, 로드맵 항목 또는 사용자와 확정한 작업에 적용한다. 작업 중 발견에 따라 DELTA를 추가하거나 분할할 수 있다. 읽기 전용 조사와 질의응답에는 작업 폴더가 필요 없다.

## 적용 기준

방식 선택과 직접 작업 기준은 `AGENTS.md`의 "작업 실행"을 따른다. 착수, 리뷰 기록, 커밋과 자동 `dev` 통합의 공통 계약은 `docs/agents/workflow-shared.md`를, 검증은 `docs/agents/verification.md`를 따른다. 이 문서는 작업 폴더, LEG, DELTA, 리뷰 지적 처리와 통합 전 커밋 정리 규칙을 정한다.

## 작업 폴더

작업 폴더 명명·추적 범위·완료 보관은 `_works/README.md`를 따른다. 작업 시작 시 `_meta.md`와 `checklist.md`를 만든다.

```text
_works/20261123-01-example/
  _meta.md
  checklist.md
  LEG-01.md          # LEG를 쓰는 작업만
  DELTA-01.md
  pending-issues/
  pending-traps/
  verification-log.md  # 검증을 실행하는 작업만
```

`_meta.md`에는 작업 브랜치, 관련 RQ·로드맵 항목(없으면 없음), 상태(진행중/완료)만 적는다. 진행 로그는 넣지 않는다. `checklist.md`에는 목표, 포함·제외 범위, DELTA 목록(LEG를 쓰면 LEG 목록), 전체 완료 조건을 적는다. 기준 문서(RQ·ADR, 참조 구현)와 대조하는 작업은 완료 조건에 차이 처리 방식을 함께 적는다. 예: "`일치` 또는 사용자 승인된 차이. 승인된 차이는 ADR의 '구현 중 확정' 절에 요약한다." 결정과 검증 근거는 해당 DELTA에 남긴다. 추가된 작업은 `DELTA-02a`처럼 기존 번호를 밀지 않고 삽입한다.

`pending-issues/`에는 GitHub 이슈 초안을, `pending-traps/`에는 장기 문서로 승격할 함정 후보를 파일 하나에 하나씩 둔다. 처리는 `workflow-shared.md`의 "문서와 최종 보고"를 따른다.

## 시작과 브랜치

착수 확인, 브랜치 이름과 기존 변경 보존은 `workflow-shared.md`의 "착수와 변경 범위"를 따른다. rubber 작업은 `dev`에서 직접 커밋하지 않는다. `_meta.md`와 `checklist.md`를 작성한 뒤 `dev`에서 임시 작업 브랜치를 만들어 진행한다. 이미 진행 중인 작업을 이어받을 때는 `_meta.md`와 기존 브랜치를 사용한다.

## LEG

LEG는 순서가 있는 DELTA 묶음이다. 작업의 DELTA가 5개 이상으로 예상되거나 처음부터 상세 계획을 세울 수 없으면 DELTA를 LEG로 묶는다. DELTA가 4개 이하로 예상되면 LEG 없이 DELTA만 쓴다.

- 크기: LEG 하나에 DELTA 2~4개를 권장하고 최대 10개까지 허용한다. 4개를 넘겨 5개 이상이 필요하면 LEG를 나눌 수 있는지 먼저 본다.
- 번호: `LEG-01`처럼 붙인다. 추가는 `LEG-02a`처럼 기존 번호를 밀지 않고 삽입한다.
- DELTA 번호: LEG와 무관하게 작업 전체에서 이어 붙인다. 예: LEG-01은 DELTA-01~03, LEG-02는 DELTA-04~06.
- 작업 시작: `checklist.md`에 LEG 목록만 적는다. 항목은 LEG 이름, 목표, 완료 조건이다. 상세 계획을 처음부터 세울 수 있는 LEG는 DELTA 목록도 적을 수 있다.
- LEG 착수: 그 LEG의 `LEG-NN.md`를 만들고 소속 DELTA와 DELTA별 상세 계획(작업 단계 포함)을 쓴다. 뒤 LEG의 상세 계획은 앞 LEG가 끝나기 전에 쓰지 않는다.
- 계획 조정: 앞 LEG의 결과가 뒤 LEG의 목표·범위를 바꾸면 그 시점에 `checklist.md`를 고친다. 전체 완료 기준의 완화나 범위 확대는 아래 "결함·후속 작업을 발견하면" 규칙대로 사용자에게 확인받는다.
- LEG 완료: LEG 착수 커밋부터 그 시점 HEAD까지 범위로 구현자와 다른 관점의 리뷰를 한 번 받고 blocker·major를 처리한다. DELTA 단위 리뷰가 필요한 DELTA(`AGENTS.md` "작업 실행"의 직접 작업으로 하지 않는 변경)는 그 리뷰를 그대로 받는다.

```markdown
# LEG-NN 제목

## 계획

- 목표:
- 착수 커밋:
- DELTA 목록과 DELTA별 예상 변경량:
- 완료 조건:

## 결과

- 상태:
- LEG 리뷰(범위, blocker·major 처리):
- 다음 LEG에 넘기는 결정·변경:
```

## DELTA 형식

각 `DELTA-NN.md`에 다음을 기록한다.

```markdown
# DELTA-NN 제목

## 계획

- 목적:
- 착수 커밋: (이 DELTA를 시작하는 시점의 `git rev-parse HEAD`. 구현자와 다른 관점 리뷰를 부를 때 이 커밋부터 그 시점 HEAD까지로 범위를 못박는 데 쓴다.)
- 변경 대상:
- 관련 RQ·ADR:
- 예상 변경량: (추가+삭제 줄. 1000줄을 넘으면 더 나누지 않는 이유를 함께 적는다.)
- 참조 범위:
- 완료 기준과 검증 방법:
- 최종 검증 대상(누적): (통합 spec 경로와 L3 스크립트. 앞 DELTA의 대상을 이어받는다.)

## 결과

- 상태:
- 변경량: (구현 완료 시점의 `git diff --shortstat` 추가+삭제. 리뷰 수정은 제외한다.)
- 테스트 정리: 지우거나 합친 테스트의 보호 계약과 대체 검증. 없으면 "정리 대상 없음"과 확인한 파일
- 실행한 검증, 소스·env 지문, 종료 상태, 통과·실패 수, 새 실행·재사용·미실행 구분:
- 최종 검증 예정 항목:
- 문서 갱신: (RQ 진행 상태, ADR "구현 중 확정", `docs/operations/`. 없으면 없음)
- 발견·처리:
- 남은 위험:

## 결정

- 판단이 필요했던 경우에만 주제·결정·근거·되돌릴 비용을 적는다.

## 리뷰 수정

- 구현 완료 뒤 리뷰·재리뷰로 고친 내용을 라운드별로 모은다. 라운드마다 커밋, 처리한 지적, 검증을 적는다.
```

DELTA마다 계획 → 변경 → 관련 검증 → 문서 갱신 → 테스트 정리(`workflow-shared.md`의 "테스트 정리") → 변경 범위 확인 → 결과 기록을 마친다. 테스트 작성·유지와 TDD 적용 여부는 `docs/agents/testing.md`를 읽고 결정한다. 검증 선택, 재사용, 증거 기록은 `verification.md`를 따른다.

`AGENTS.md` "작업 실행"의 직접 작업으로 하지 않는 변경을 담은 DELTA는 실패 시나리오를 검증에 포함하고(DB를 쓰면 실제 PostgreSQL), 구현자와 다른 관점의 리뷰를 완료 조건에 넣는다. 리뷰 범위는 `workflow-shared.md`의 "리뷰 기록"에 따라 착수 커밋부터 그 시점 HEAD까지로 명시한다.

DELTA 하나의 변경은 1000줄 정도를 권장하고 최대 2000줄까지 허용한다. 줄 수는 추적 파일의 `git diff --shortstat` 추가+삭제이며 테스트를 포함한다. `pnpm-lock.yaml`은 제외한다.

- 계획: DELTA마다 예상 변경량을 적는다. 1000줄을 넘을 것으로 보이면 먼저 더 나눌 수 있는지 본다. 나누지 않으면 이유를 적는다. 예상이 2000줄을 넘으면 계획 단계에서 나눈다.
- 작업 중: 1001줄은 분할 사유가 아니다. 변경량을 이유로 DELTA를 추가하지 않고 현재 DELTA를 끝낸다. 2000줄을 크게 넘을 것이 확실해진 경우에만 남은 부분을 `DELTA-NNa`로 분리한다.
- 측정: 구현 완료 시점의 변경량으로 한도를 확인한다. 리뷰 수정과 그 뒤 보완은 DELTA 문서 "리뷰 수정" 절에 모으고 한도에 넣지 않는다.
- 초과: 구현 완료 시점에 2000줄을 넘으면 초과량과 원인을 결과에 적고, 같은 LEG의 남은 DELTA 계획에 반영한다.

`참조 범위`에는 이 DELTA에 필요한 기준 문서의 파일과 절(RQ 번호, ADR 결정 번호)만 적는다. 작업자와 리뷰어는 그 범위만 읽는다. 여러 DELTA가 나눠 쓰는 대조표는 대조 단위(API operation 등)별 파일로 나눈다. 범위 밖 내용이 필요하면 읽고 DELTA 결과에 이유를 적는다.

결함·후속 작업을 발견하면 `pending-traps/`, `pending-issues/`에 기록하고 현재 DELTA의 완료 기준을 먼저 지킨다. 뒤 DELTA와 충돌하는 결정은 지금 checklist에 반영한다. 필요한 만큼 DELTA를 추가·분할하되 전체 완료 기준의 완화나 범위 확대는 사용자에게 확인받는다. 확인은 필요가 처음 드러난 DELTA에서 받고 마지막 DELTA로 미루지 않는다. RQ·ADR과 다른 동작이 처음 나오면 그 시점에 처리 방식을 확인받는다. 계획한 검증 범위보다 크거나 위험한 환경(sudo가 필요한 NFS, Docker 권한)이 필요하면 실행 전 범위를 다시 정한다.

## 리뷰 지적 처리

심각도는 `workflow-shared.md`의 "리뷰 기록"을 따른다. 리뷰 지적은 현재 DELTA가 추가·변경한 동작에서 드러났는지로 나눈다.

- 현재 DELTA 동작의 blocker·major: 이 DELTA에서 수정하고 수정분만 재리뷰한다. 수정으로 테스트를 더하거나 고쳤으면 테스트 정리를 다시 한다.
- 현재 DELTA 동작의 minor: 같은 수정 라운드에서 처리할 수 있으면 처리하고, 재리뷰는 열지 않는다. 처리하지 않으면 기록한다.
- 기존 결함과 범위 밖 개선: 수정하지 않고 `pending-issues/`에 초안을 남긴다. 등록은 `workflow-shared.md`의 "문서와 최종 보고"를 따른다. 전체 완료 조건을 직접 막는 경우에만 사용자 확인 후 DELTA를 추가해 처리한다.
- 재리뷰에서 새로 나온 minor: 수정 라운드를 다시 열지 않고 기록한다.

## 리뷰와 다음 DELTA 겹치기

DELTA-N 리뷰가 진행되는 동안 다음 조건을 모두 만족하면 DELTA-N+1 변경을 시작한다. 하나라도 어긋나면 DELTA-N 리뷰 처리가 끝난 뒤 시작한다.

- DELTA-N 변경이 커밋되어 있고, 리뷰는 그 커밋 범위의 diff를 기준으로 한다.
- DELTA-N+1 계획의 변경 대상 파일이 DELTA-N 변경 파일과 겹치지 않는다.
- DELTA-N+1이 DELTA-N에서 리뷰로 바뀔 수 있는 결과(스키마, 모듈 `index.ts` 공개 인터페이스, `AttemptOutcome` 같은 모듈 간 계약, problem+json 오류 변환)에 의존하지 않는다.

겹쳐 진행하는 DELTA는 한 번에 하나다. DELTA-N 수정은 DELTA-N 변경 파일 안에서 하고 해당 파일만 선택해 따로 커밋한다. 수정이 DELTA-N+1 변경 파일에 닿아야 하면 DELTA-N+1 작업을 멈추고 DELTA-N 수정을 먼저 끝낸다. DELTA-N 결과 기록은 리뷰 처리 후에 작성하고, DELTA-N+1 완료 전에 DELTA-N 리뷰 처리를 끝낸다.

## 이어받기와 마무리

이어받는 사람은 `_meta.md`의 상태, 브랜치, `checklist.md`, 결과가 비어 있는 마지막 LEG(LEG를 쓰는 경우), 마지막으로 결과가 비어 있는 DELTA 순서로 읽는다. 파일이나 브랜치가 없으면 추측해 새 작업으로 취급하지 않는다.

각 DELTA가 끝나면 해당 작업 파일만 선택해 로컬 커밋한다. 임시 작업 브랜치에서는 작업자가 필요한 만큼 자유롭게 커밋할 수 있다. 작업의 완료 조건을 충족하면 임시 작업 브랜치의 변경을 자동으로 `dev`에 fast-forward(`git merge --ff-only`)로 통합한다. 통합 시 작업 커밋을 의미 단위로 줄여 `dev`에는 정리된 커밋만 남긴다. 병합 커밋(`--no-ff`)과 임시 브랜치의 중간 커밋은 `dev`에 남기지 않는다. 통합이 끝나면 임시 작업 브랜치를 삭제한다. 공통 통합 조건과 금지 명령은 `workflow-shared.md`의 "커밋과 자동 dev 통합"을 따른다.

커밋을 재그룹화하고 병합할 때는 다음 순서를 따른다. 작업 전체를 커밋 하나로 줄여도 되면 3단계에서 묶음 하나만 만든다.

1. 현재 임시 작업 브랜치의 HEAD를 백업 ref로 보존한다: `git update-ref refs/backup/<브랜치>-pre-merge HEAD`.
2. `git log --oneline --name-only dev..HEAD`로 커밋을 의미 단위로 묶는다.
3. `git switch --detach dev` 후 각 묶음마다 `git cherry-pick -n <커밋...>`으로 변경을 적용하고 정리된 커밋을 만든다.
4. 백업 ref와 결과 HEAD의 트리를 비교한다: `git diff refs/backup/<브랜치>-pre-merge HEAD`. 의도적으로 제외한 변경이 없다면 출력이 없어야 한다.
5. 트리가 일치하면 임시 작업 브랜치를 결과 HEAD로 옮기고(`git branch -f <브랜치> HEAD`) `git switch dev && git merge --ff-only <브랜치>`로 통합한다.
6. 통합 후 백업 ref(`git update-ref -d refs/backup/<브랜치>-pre-merge`)와 임시 작업 브랜치를 삭제한다.

트리 비교가 다르거나 fast-forward가 불가능하면 통합을 멈추고 차이를 보고한다.

후속 이슈 등록, 함정 승격과 최종 보고는 `workflow-shared.md`의 "문서와 최종 보고"를 따른다. 결과를 확인한 후 작업 폴더를 `_works/README.md`의 "완료와 보관"에 따라 보관한다.

# 로드맵

RQ-001~039 이후의 장기 방향이다. 확정한 요구사항이 아니라 방향 결정이다. 항목을 구현하기 전에 RQ와 ADR로 확정하고, 확정되면 이 문서에는 위치(RQ·ADR 번호)만 남긴다.

2026-11-23에 외부 제안 메모(요구사항 정의서 v1.1, 저장소에 추적하지 않음)를 현재 RQ·ADR과 대조해 정리했다. 같은 날 다른 세션(mailo-fc)이 코드·문서를 근거로 검토한 의견을 반영했다. 메모의 RQ 번호는 이 저장소의 번호와 다르므로 쓰지 않는다.

## 판단 기준

- 여러 호출처에 쓸모가 있는가. 한 호출처의 사정이면 받지 않는다.
- 운영 의존성을 늘리지 않는가(RQ-029). 브로커, 외부 메일 서버, 새 상시 서비스를 추가하지 않는다.
- 승인된 ADR의 결정과 충돌하지 않는가. 충돌하면 새 ADR로 대체할 이유가 있을 때만 받는다.
- 메일 내용·주소·인증 정보를 새 경로로 노출하지 않는가(RQ-027).

## 이미 구현했거나 결정한 항목

| 메모의 제안 | 현재 위치 |
| ----------- | --------- |
| 요청 우선순위와 굶음 방지 | RQ-033~038, ADR-0009 |
| 호출처별 격리와 할당 | RQ-032(`sendQuota24h`) |
| 요청별 TTL | RQ-039, ADR-0010 |
| SMTP 오류 분류, 결과 불명(`DATA` 단계) | RQ-009, RQ-013, ADR-0003·0007 |
| 일부 수신자 거부 | ADR-0007 결정 7(`SENT`, `rejectedRecipients` 노출) |
| 차단기 상태의 DB 공유와 `half_open` 대표 작업 | ADR-0007 |
| 호출처 키 `kid`와 이전 키 공존, 지문(HMAC) | RQ-022, RQ-011, ADR-0008 |
| 트랜잭셔널 outbox 가이드 | RQ-021, `samples/spring-boot-relay/` |
| 템플릿·첨부 제외 | 메모도 제외를 권장한다. 첨부는 ADR-0004·RQ-002가 미지원으로 정했다 |

## 순서

순서는 6 → 8 → 7 → 9 → 10이다. 이유는 다음과 같다.

- 단계 8의 지표를 처음부터 `account="default"` 라벨로 내면 단계 7 뒤에도 지표 이름이 바뀌지 않는다.
- 단계 7은 점유 쿼리를 다시 쓰므로 대기 건수 지표가 있어야 비용을 측정한다.
- 운영 토큰 권한 분리는 단계 8의 `/metrics`보다 먼저, 단계 6에서 정한다.

## 단계 6. 운영 제어와 호출처 보호

운영자가 장애 때 손으로 할 수 있는 일을 정한다. 현재는 `GET /health/ready`(운영자 토큰)의 읽기 전용 수치뿐이다. 새 ADR 하나로 묶어 정한다.

| 항목 | 결정 | 근거·주의 |
| ---- | ---- | --------- |
| 운영 토큰 권한 | 읽기 토큰(헬스·지표)과 관리 토큰(정지·취소)으로 나눈다 | 현재 운영 토큰은 하나이고 호출처 키와 같은 Bearer 경로로 판정한다. 단계 8의 `/metrics`를 같은 토큰으로 열면 정지·취소 권한 토큰이 Prometheus 설정에 놓인다 |
| 발송 일시 정지 | DB에 저장한다. 키는 처음부터 범위(전체·계정·호출처)로 둔다. 정지 판정은 점유 경로와 대표 작업(`half_open`) 점유 경로 양쪽에 넣는다 | 범위 키로 두면 단계 7에서 다시 마이그레이션하지 않는다. 정지는 `/health/ready`의 200/503에 반영하지 않는다(RQ-031). 운영자 응답과 로그에만 둔다. 정지 중에도 TTL은 흐르므로 긴 정지는 `EXPIRED`를 대량으로 만든다. 운영 문서에 경고를 쓴다 |
| 호출처 단위 정지 | 단계 6에 포함한다. 정적 설정(`enabled` 필드)이 아니라 DB 정지로 처리한다 | 레지스트리에서 호출처를 빼도 큐의 작업은 계속 발송된다. 그 호출처는 REST 인증을 잃어 조회·이벤트도 못 읽는다. 기존 `caller_id <> ALL` 제외 경로를 재사용한다 |
| 작업 취소 | `PENDING`·`RETRY_WAIT`만 `CANCELED`로 바꾼다. 취소 요청은 멱등이다. 호출처 API 키로 자기 작업을, 관리 토큰으로 모든 작업을 취소한다 | 바꿀 CHECK는 `mail_jobs.status`, `mail_jobs_terminal_state`, `mail_events.type` 셋이다. 종결 이벤트(`JOB_CANCELED`)를 남긴다 |
| 취소의 선행 작업 | 구현 전에 API 문서에 "모르는 이벤트 종류와 상태는 무시하지 않고 미종결로 두지 않는다" 규칙을 쓰고, Java 샘플을 고친다 | 샘플 폴러는 모르는 이벤트를 경고만 하고 건너뛴다. 취소된 작업의 outbox 행이 영원히 미종결로 남는다 |
| 실패 작업 재시도 | 운영자 재시도 API는 만들지 않는다. 호출처가 새 Key로 다시 제출한다. Mailo는 작업 조회에 "결과 불명 가능"을 표시한다 | 운영자가 만든 작업은 호출처가 Key로 매칭하지 못한다(ADR-0005 결정 8). outbox 행은 실패인데 메일은 발송된다. 본문은 종결 뒤 기본 1일(`MAILO_BODY_RETENTION_SECONDS`) 지나면 삭제되고, 본문 암호화의 AAD가 작업 ID라 암호문을 복사하지 못한다 |
| 감사 기록 | 관리 작업(정지·재개·취소)을 DB에 기록한다. 항목은 토큰 식별 이름, 동작, 범위, 대상 ID, 시각이다 | 운영자 이름·사유를 자유 텍스트로 받아 로그에 쓰지 않는다(로그에 요청 값 금지). 호출처 등록·키 교체는 파일 설정이라 저장소 이력이 감사 기록이다 |
| 운영 CLI | 같은 이미지에서 `node dist/cli.js`로 실행한다. 상주 프로세스가 없다. 운영 REST를 호출한다. 읽기 명령(`status`, `jobs show`, `queue stats`)을 먼저 낸다 | 변경 명령은 운영 REST가 먼저 있어야 한다 |
| 호출처별 수신 도메인 허용 목록 | 레지스트리에 `allowedRecipientDomains`를 둔다. 생략하면 제한 없음이다. 위반하면 새 오류 코드로 거부한다 | API 키 유출이나 스테이징 오설정 때 임의 수신자로 대량 발송되는 것을 막는다. `allowedFrom`과 대칭이다. 오류에 주소를 넣지 않는다(RQ-027). 마이그레이션은 없다 |
| 이벤트 피드 공백 감지 | cursor가 보존 범위(기본 30일)보다 오래되면 명시 오류(410 계열)를 낸다 | 30일 넘게 폴링을 멈춘 호출처가 이벤트 유실을 모른다. cursor 형식은 ADR-0006 결정 7 그대로다 |

마이그레이션은 `CANCELED`용 CHECK 교체와 발송 제어 테이블, 감사 테이블이다. 롤링 호환은 0003·0004의 `NOT VALID` 방식을 따른다. 이전 버전 인스턴스는 `CANCELED`를 응답에 그대로 내보낸다. 롤링 배포 중 문제가 될지는 확인하지 않았다.

## 단계 8. 관측성

- `GET /metrics`(Prometheus 텍스트 형식, 읽기 토큰). 지표는 대기·재시도 대기·처리 중 건수, 가장 오래 대기한 작업의 경과 시간, 종결 건수, SMTP 오류 분류별 건수, 차단기 상태, lease 회수 횟수, 이벤트 피드 지연이다.
- 전역 값(큐 건수)은 gauge로, 인스턴스 값은 counter로 구분한다. 인스턴스마다 전역 큐 수치를 내면 합산할 때 N배가 된다. 이름 규칙에 쓴다.
- `dueCount`는 10000에서 잘린다. 지표에도 잘림 표시를 둔다.
- 라벨은 `caller_id`, `account_id`, 사유 코드만 쓴다. SMTP 응답 텍스트와 주소는 넣지 않는다(ADR-0007 구현 중 확정 5).
- 단계 7 전에는 `account="default"` 하나를 낸다.
- 알림은 Mailo가 보내지 않는다. 알림 규칙 예시(차단기 열림, 적체, 최종 실패 급증)를 운영 문서에 둔다(RQ-029).
- 새 npm 의존성 없이 텍스트 형식을 직접 쓸 수 있는지 먼저 본다. 의존성을 추가하면 이유를 적는다.
- 미결정 항목 "비기능 요구(처리량 목표, 메트릭)"를 닫는다. 처리량 목표는 측정 뒤에 정한다.

## 단계 7. 다중 SMTP 계정

가장 큰 구조 변경이다. 새 ADR에서 아래를 모두 정한다. 현재는 SMTP 설정 하나와 전역 차단기 하나다.

- 계정 프로필은 호출처 레지스트리와 같은 방식이다. JSON에는 변수 이름(`secretVar`)만 두고 값은 `<변수>_FILE`이나 `<변수>`로 받는다.
- 계정 ID는 운영자가 정한 불투명 이름이다. SMTP 사용자 주소를 로그·지표 라벨에 쓰지 않는다(RQ-027).
- 호출처가 계정 하나를 참조한다. 생략하면 기본 계정이다.
- 작업은 등록 때 `mail_jobs.account_id`로 계정을 고정한다. 전송 때 호출처→계정 매핑을 다시 읽지 않는다. 이유는 다음과 같다.
  - `from`을 생략한 작업은 전송 때 기본 발신 주소로 채워진다. 발신 주소 허용 판정은 등록 때 한다. 매핑이 바뀌면 검증한 `From`과 다른 계정으로 나간다.
  - claim과 결과 기록이 다른 차단기 행을 갱신할 수 있다.
  - 재시도 사이에 `Message-ID` 도메인이 바뀐다.
  - 전송 때 계정 프로필이 없으면 `internal: true` 오류로 처리한다. 차단기는 건드리지 않는다.
- 차단기는 계정별로 독립한다. 계정 행을 마이그레이션으로 넣을지 기동 때 upsert할지 정한다(행이 없으면 현재는 예외다).
- 점유는 계정별로 나눈다. 현재 claim 한 번은 모드 하나를 쓴다.
  - 계정 하나가 일일 한도로 한 시간 닫히면, 모든 인스턴스가 그 계정 대기 작업을 매 poll마다 읽고 버린다. 지금은 단일 차단기가 열리면 아무것도 읽지 않는다. 흔한 장애에서 비용이 나빠진다.
  - `(account_id, priority DESC, next_attempt_at, id)` 부분 인덱스, 계정별 `LATERAL` 점유, 계정별 대표 작업을 정한다.
  - 인덱스는 `CREATE INDEX CONCURRENTLY`로 단독 파일(`-- mailo:no-transaction`)에 둔다.
  - 호출처별 동시 처리 상한을 이 재작성과 같이 한다. `mail_jobs_sending_caller_idx`를 쓴다. advisory lock은 계정용 클래스를 따로 둔다.
- 계정별 24시간 할당은 RQ-032 방식을 재사용한다. 초·분 단위 토큰 버킷은 만들지 않는다. 한도 수치를 확인하지 못했다. 이 할당은 ADR-0007 구현 중 확정 7의 한계(호출처 할당 합이 계정 한도를 넘지 않는다는 보장 없음)를 보완한다.
- 레지스트리는 모르는 필드를 거부한다. 새 필드가 든 레지스트리를 이전 버전이 읽으면 기동하지 못한다. "코드 먼저, 레지스트리 나중" 배포 순서를 ADR-0009 결정 10처럼 명시한다.
- 인증 없는 `/health/ready`는 지금 `circuitBreaker.state` 하나를 낸다. 다계정일 때 공개 응답 형태를 정한다. 공개 응답에 계정 목록을 넣지 않는다.
- `allowedFrom`을 계정 단위로 올릴지 호출처 단위로 둘지 정한다.
- 선행 확인: Gmail 인증 모드에서 `allowedFrom` 주소가 send-as 별칭이어야 `From`이 유지되는지(미결정 항목).
- 미결정 항목 "차단기 키 구성"과 "계정 전체 발송 속도 제어"를 닫는다.

## 단계 9. 호출처 도구와 문서

- 프로토콜 적합성 자료: JWS 서명 입력, JWE 복호화 결과, 기대 판정(수락 또는 사유 코드)의 골든 벡터를 `docs/api/`에 둔다. 지문은 서버 비밀키 HMAC이라 호출처가 계산·검증할 수 없으므로 벡터에 넣지 않는다. Java 샘플이 한 조합을 확인했다.
- 암호화 키 분실·유출 대응 절차를 `key-management.md`에 쓴다. ADR-0008·RQ-022에 미결정으로 남아 있다.
- DB 유지보수 안내: 테이블 팽창·VACUUM 점검, 파티셔닝 검토 기준. 파티셔닝 구현은 하지 않는다.
- 레지스트리 재로드: 변경이 재시작 뒤에 반영된다(RQ-032 한계). 롤링 재시작으로 충분한지 운영 경험으로 판단한다.

## 단계 10. 개인정보 최소화와 결과 불명 정책

둘 다 승인된 ADR의 결정을 바꾸므로 각각 새 ADR이 먼저다. 방향만 정한다.

| 항목 | 방향 | 충돌하는 결정 |
| ---- | ---- | ------------- |
| 수신자 주소 보존 단축 | 수신자는 `mail_jobs`·`mail_events`에 평문으로 30일 남고 본문은 기본 1일 뒤 지워진다. 유예 뒤 주소를 HMAC이나 건수로 바꾼다. DB·백업의 개인정보 노출면이 줄어든다 | ADR-0006 결정 2, ADR-0007 결정 7, RQ-016, RQ-017(실패 이벤트에 수신자를 넣는다). 유예 기간과 실패 알림 필요 정보의 균형을 정해야 한다 |
| 결과 불명 처리 opt-in(`onUncertainOutcome: retry\|fail`) | OTP·영수증처럼 중복이 손실보다 나쁜 메일에 선택지를 준다. `fail`이면 재시도하지 않고 `OUTCOME_UNKNOWN` 사유로 종결한다. 대상은 `DATA` 단계 타임아웃과 lease 회수다. 정확히 한 번은 보장하지 않는다 | ADR-0001 결정 5, ADR-0002 결정 5, ADR-0007 결정 3. 요청별 예외를 정하고 지문 `policy`에 넣는다(ADR-0009 결정 4 방식) |

## 보류하는 항목

| 항목 | 보류 이유 | 재검토 조건 |
| ---- | --------- | ----------- |
| 운영자 실패 작업 재시도 API | 호출처가 Key로 결과를 매칭하는 구조와 맞지 않고 본문이 1일 뒤 지워진다(단계 6 표) | 호출처가 호출처 인증으로 재시도하는 `retryOf` 방식을 요구한다. 복호화 후 재암호화가 필요하다 |
| 예약 발송(`notBefore`) | RQ-039가 범위 밖으로 정했다. 구현은 작다(`next_attempt_at`). 문제는 TTL 기준이다. 접수 기준이면 예약이 TTL을 넘긴다 | 호출처 둘 이상이 요구한다. TTL을 예약 시각부터 세는지 정한다 |
| 첨부파일 | 저장 용량, 악성 파일, 암호화 저장이 DB 하나라는 구조(RQ-029)를 압박한다. ADR-0004가 미지원으로 정했다 | 호출처 둘 이상이 요구한다. 크기 상한과 보존을 포함한 새 ADR |
| 호출처용 TypeScript SDK | 호출처가 Java 등 다른 언어다. 패키지를 새로 나누지 않는 규칙(AGENTS.md)과 충돌한다. 적합성 자료(단계 9)가 먼저다 | TypeScript 호출처가 둘 이상이고 서명·암호화 구현 실수가 반복된다 |
| webhook 결과 통지 | ADR-0006이 pull 피드로 정했다. webhook은 자체 재시도 큐가 필요해 두 번째 outbox가 된다 | 피드 폴링으로 해결되지 않는 호출처가 나온다. 별도 ADR |
| 수신자별 작업 분리 | 일부 거부는 `SENT`로 처리하고 거부 수신자를 노출한다(ADR-0007 결정 7) | 일부 수락 뒤 재발송이 필요한 사례가 나온다 |
| 모의 발송(sink) 호출처 모드 | 실제 서명·암호화·이벤트 계약으로 통합 시험하는 값은 있다. 그러나 개발용 Mailpit profile이 같은 계약을 거쳐 실제 SMTP 수락까지 시험한다. 운영 레지스트리에서 잘못 켜면 메일이 조용히 사라지고 `SENT` 의미(RQ-016)가 흐려진다 | Mailpit으로 못 하는 대량 부하 측정이 필요해진다 |
| 반송(Bounce) 추적 | 범위 밖으로 정했다. 별도 수신 경로가 필요하다 | 호출처가 요구한다 |
| 운영 웹 UI | CLI와 운영 REST로 시작한다 | CLI로 운영이 어렵다는 근거가 쌓인다 |

## 받지 않는 항목

| 항목 | 이유 |
| ---- | ---- |
| SMTP 계정 자동 전환(failover) | 메모도 권장하지 않는다. 계정 전환은 발송 한도 우회가 되고 발신 주소 인증 문제가 생긴다. 단계 7의 계정별 차단기와 계정 단위 정지로 운영자가 판단한다 |
| 등록 단계의 호출처별 대기 건수 제한과 429 | ADR-0005 결정 5와 ADR-0007 결정 10이 등록 응답에 429를 쓰지 않기로 정했다. 우선순위(RQ-033)와 발송 할당(RQ-032)으로 굶음을 막는다 |
| 발송 템플릿 | 메시지 생성은 호출처의 책임이다. 메모도 제외를 권장한다 |
| 메모의 기본값 제안(TTL 24시간, 재시도 5회) | 현재 값은 RQ-008과 ADR-0010이 정했다. 메모는 자기 값을 초기 제안이라고 밝힌다 |

## 검증하지 않은 가정

- Gmail·Workspace의 계정별 한도 수치와 관리 설정에 따른 차이는 확인하지 않았다. 단계 7의 할당 기본값은 정하지 않고 운영자가 설정한다.
- 계정별 점유 분할의 쿼리 비용은 측정하지 않았다. 현재 수치는 대기 10만 건에서 poll당 11.8ms(ADR-0007 구현 중 확정 10)다. 단계 8의 대기 건수 지표 뒤에 측정한다.
- 이전 버전 인스턴스가 `CANCELED`를 그대로 내보내는 동작이 롤링 배포에서 문제가 되는지는 확인하지 않았다.
- 검토 의견의 파일·줄 근거 중 일부(`status`·`terminal_state` CHECK, 레지스트리의 모르는 필드 거부, 본문 보존 1일)만 직접 확인했다. 나머지는 단계별 ADR을 쓸 때 코드로 다시 확인한다.
- 운영 REST를 CLI가 호출하는 구조의 토큰 전달 방식은 확인하지 않았다.

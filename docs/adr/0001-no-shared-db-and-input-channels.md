# Mailo와 사용처는 DB를 공유하지 않으며, 발송 요청 입력 채널은 REST와 파일로 한정한다

## 상태

승인됨 (2026-11-23)

ADR-0005~0008 승인(2026-11-23)으로 결과 절과 미확정 절을 갱신했다. 결정 1~7은 바뀌지 않는다.
결정 6의 암호화 형식은 ADR-0008 결정 1이 JWE(`RSA-OAEP-256`, `A256GCM`)로 구체화한다.

## 배경

Mailo는 Gmail·Google Workspace SMTP로 이메일을 비동기 발송하는 경량 시스템이다.
요구사항은 다음 세 가지 입력 방식을 제시했다.

- REST API 호출
- 특정 폴더에 메일을 파일로 저장
- PostgreSQL DB에 저장

요구사항 RQ-021은 메일 발송 실패가 사용처의 비즈니스 트랜잭션에 영향을 주지 않을 것을 요구한다.
RQ로 옮기기 전의 원문 요구사항은 파일 저장만으로는 DB 트랜잭션과의 원자성이 보장되지 않는다고 적고 있다.

원자성을 얻으려면 발송 요청 행이 비즈니스 데이터와 같은 DB 트랜잭션에 들어가야 한다.
이는 Mailo와 사용처가 DB를 공유해야 한다는 뜻이다.
공유 DB는 Mailo가 사용처의 스키마와 접근 권한에 묶이므로 채택하지 않는다.

## 결정

1. **Mailo는 NestJS 기반 독립 서비스다.**
   - Spring Boot 내부 모듈이나 Java 라이브러리로 만들지 않는다.
2. **Mailo와 사용처는 DB를 공유하지 않는다.**
   - 사용처가 Mailo DB에 접속하지 않는다.
   - Mailo가 사용처 DB에 접속하지 않는다.
   - Mailo DB는 Mailo만 접근하는 내부 저장소다.
3. **Mailo의 발송 요청 입력 채널은 REST와 파일 두 가지다.**
   - "PostgreSQL DB에 저장" 채널은 Mailo의 입력 채널에서 제외한다.
4. **사용처가 DB 트랜잭션과 원자성이 필요하면 사용처 쪽에서 outbox + relay 패턴을 쓴다.**
   - 사용처가 자기 DB의 outbox 테이블에 발송 요청을 같은 트랜잭션으로 쓴다.
   - 커밋 후 relay가 REST 또는 파일 채널로 Mailo에 전달한다.
   - Mailo는 outbox를 알지 못한다.
5. **Mailo가 보장하는 범위는 멱등한 요청 등록과 at-least-once 발송이다.**
   - 사용처 비즈니스 트랜잭션과의 원자성은 Mailo가 보장하지 않는다.
   - 원자성은 결정 4의 사용처 outbox가 담당한다.
   - 같은 `Idempotency-Key`로 재요청해도 중복 등록되지 않는다.
6. **호출처는 요청 본문을 봉투 암호화해서 보낼 수 있다. 사용 여부는 호출처가 선택한다.**
   - 파일·REST 채널이 같은 암호화 형식을 쓴다.
   - 호출처가 암호화한 본문은 Mailo가 수집 시 복호화한다.
   - 암호화 범위는 본문(text·html)과 제목이다.
   - 수신자와 `Idempotency-Key`는 평문이다. Mailo가 검증·중복 판단·라우팅에 쓰기 때문이다.
7. **Mailo는 DB에 저장하는 본문을 항상 암호화한다.**
   - 호출처의 봉투 암호화 사용 여부와 무관하다.
   - 키는 Mailo가 관리한다.

## 암호화 범위와 한계

암호화는 Mailo에 도달하기 전과 Mailo 저장소 안의 노출을 줄이는 수단이다.

- SMTP 전송 시점에 Mailo는 본문을 평문으로 복호화한다.
- 수신자 구간의 종단 간 암호화(S/MIME, PGP)는 범위 밖이다.
- Mailo 프로세스가 복호화 키를 가지므로 Mailo 호스트나 메모리가 침해되면 보호되지 않는다.
- 막는 대상은 파일 폴더, 백업, NAS, DB 덤프를 통한 유출이다.

## 파일 채널 사용 시 주의

파일 채널은 발송 실패가 비즈니스 트랜잭션에 영향을 주는 것을 줄인다.
파일 쓰기는 DB 트랜잭션 밖에 있으므로 원자성은 없다.

- 커밋 전에 쓰면, 이후 롤백될 때 업무상 존재하지 않는 건의 메일이 발송된다.
- 커밋 후에 쓰면, 쓰기 전에 프로세스가 죽을 때 메일이 유실된다.

사용처에는 커밋 후 쓰기를 권한다.
유실 가능 구간이 남는 점은 사용처 문서에 명시한다.

파일 채널은 파일시스템 권한이 유일한 인증이다.
본문이 디스크에 평문으로 남을 수 있으므로 위 결정 6의 봉투 암호화를 선택할 수 있다.
접근 통제와 위조 방지 방식은 ADR-0004가 정한다.

## 결과

- 구현 구조와 요청 인터페이스(RQ-001~003)가 확정된다.
- 실패 알림(RQ-017) 후보는 다음 세 가지였고, ADR-0006이 이벤트 피드 pull 방식으로 정했다.
  - 사용처가 REST로 상태를 조회한다. 이벤트 피드가 이 방식을 확장한다.
  - Mailo가 지정 폴더에 최종 실패 파일을 쓴다. 채택하지 않았다.
  - Mailo가 사용처 HTTP endpoint로 webhook을 보낸다. 채택하지 않았다.
- 사용처에서 outbox + relay를 구현하는 비용이 생긴다.
  - Spring Boot starter 제공 여부는 Mailo 본체 범위 밖의 별도 결정이다.

## 미확정

이 ADR 작성 시점에 확정하지 않았던 항목과 현재 상태다. 모두 결정됐다.

- Mailo 내부 큐 저장소: ADR-0002에서 결정했다.
- 파일 채널의 형식, 폴더 구조, 접근 통제, 서명, 폴더 배치 환경: ADR-0004에서 결정했다. 격리 폴더(`rejected/`)는 ADR-0006 결정 4가 폐지했고, HMAC 서명은 ADR-0008 결정 2가 JWS로 대체했다.
- `Idempotency-Key` 필수 여부: 파일 채널은 ADR-0004에서, REST까지의 확대는 ADR-0005 결정 1에서 결정했다.
- `Idempotency-Key` 유일성 범위, 보존 기간, 같은 Key에 다른 내용이 올 때의 처리: ADR-0005 결정 2~4, 7.
- 실패 알림 방식: ADR-0006. 이벤트 피드 pull 방식이다.
- 봉투 암호화의 알고리즘, 키 식별자(`kid`) 형식, 키 교체 절차, 키 배포 방식: ADR-0008 결정 1, 5. 키 배포는 호출처에 Mailo 공개키만 주는 방식이다.
- Mailo DB 본문 암호화 키의 보관 방식, 본문 보존 기간과 삭제 정책: ADR-0008 결정 6, 7.
- 첨부파일 지원 여부와 크기 제한: 1·2단계 모두 지원하지 않는다. `attachments` 필드가 오면 REST는 400, 파일은 수집 거부로 처리한다. 필요해지면 별도 ADR로 정한다.

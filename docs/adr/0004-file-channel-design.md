# 파일 채널은 호출처별 폴더에 JSON 파일을 rename으로 넣고, Mailo가 폴링으로 수집한다

## 상태

승인됨 (2026-11-23)

2026-11-23 2단계에서 구현했다(같은 호스트 로컬 파일시스템 대상). 구현 세부와 추정과 다른 점은 "구현 중 확정" 절을 따른다.
검증 범위는 PostgreSQL 통합 테스트와 임시 디렉터리다. NAS/NFS, Docker 볼륨 마운트, 공용 그룹·setgid·ACL 권한 모델은 검증하지 않았다(결정 8·10은 3단계 확인 대상).
2026-11-23 3단계에서 같은 호스트 Docker named volume의 권한 모델을 스크립트로 검증했다("구현 중 확정" 13~19). NAS/NFS는 이 검증 범위가 아니다.
2026-11-23 3단계에서 같은 호스트 NFS loopback(NFSv4.1·4.2, `root_squash`, non-root UID)에서 파일 채널을 검증하고 `ESTALE` 처리를 고쳤다("구현 중 확정" 20~27). 실제 NAS 제품은 검증하지 않았다.
2026-11-23 3단계 마무리에서 사용자 위임 결정으로 결정 8의 권한 문구를 보완했다("구현 중 확정" 28, 결정 8에 "보완됨" 표기). 결정 원문은 지우지 않았다.

2026-11-23 리뷰 반영으로 결정 3·5·8을 보강했다.
ADR-0005~0008 승인(2026-11-23)으로 다음이 바뀌었다. 원문은 유지하고 해당 위치에 "대체됨" 표기를 붙인다.

- ADR-0005 결정 1: Key를 REST까지 필수로 확대했다. 결과 절의 Key 관련 서술을 갱신했다.
- ADR-0006 결정 4: 결정 2·7의 `rejected/` 폴더를 폐지했다. 수집 거부는 원본을 삭제하고 DB에 기록한다(ADR-0006 결정 3).
- ADR-0008 결정 2: 결정 9의 HMAC 서명을 JWS로 대체했다. 서명 파일의 최상위는 flattened JWS이고 요청 JSON은 `payload` 안에 있으며, 결정 1의 공통 스키마는 `payload`에 적용한다.
- ADR-0008 결정 3: 결정 5의 3~6단계를 ADR-0008의 수집 순서가 대체한다.

## 배경

ADR-0001이 파일을 입력 채널로 정했다.
요구사항 RQ-002는 파일 수집 규칙을, RQ-024는 접근 통제를 요구한다.

파일 채널의 제약은 다음과 같다.

- 파일시스템 권한이 유일한 인증이다.
- 파일 쓰기는 사용처 DB 트랜잭션 밖에 있다(ADR-0001).
- 폴더 배치 환경으로 같은 호스트의 Docker 볼륨과 NAS/NFS를 모두 지원해야 한다.
- NAS/NFS에서는 파일 변경 이벤트(inotify)에 의존할 수 없다.
- 본문이 디스크에 평문으로 남을 수 있다. 봉투 암호화는 호출처 선택이다(ADR-0001 결정 6).
- 같은 파일이 두 번 수집될 수 있다. 큐 등록 후 파일 정리 전에 Mailo가 종료되는 경우가 해당한다.

## 결정

1. **발송 요청 한 건은 JSON 파일 하나다.**
   - 필드는 REST 요청 본문과 같은 공통 스키마를 쓴다.
   - 파일 채널은 `version`과 `idempotencyKey`를 추가로 요구한다. REST도 Key가 필수다(ADR-0005 결정 1). REST는 `Idempotency-Key` 헤더를 쓴다.
   - 봉투 암호화를 쓰면 `subject`·`text`·`html` 대신 암호문과 키 정보(`kid` 등)를 넣는다. 형식은 ADR-0008 결정 1의 JWE(`content` 필드)다.
   - 서명을 쓰는 호출처의 파일은 최상위가 flattened JWS이고 요청 JSON이 `payload` 안에 있다(ADR-0008 결정 2).
   - 스키마의 필드명과 암호문 형식은 설계 문서에서 확정한다.
2. **폴더 구조는 호출처별 입력 폴더와 Mailo 전용 격리 폴더다.** 대체됨(일부): ADR-0006 결정 4. `rejected/`는 두지 않는다.
   - `<root>/inbox/<caller>/`: 호출처가 파일을 넣는 폴더.
   - `<root>/rejected/<caller>/`: 수집에 실패한 파일을 두는 Mailo 전용 폴더. 대체됨: ADR-0006 결정 4.
   - `processing/`, `done/` 폴더는 두지 않는다.
3. **호출처는 임시 이름으로 쓴 뒤 같은 폴더 안에서 rename한다.**
   - 쓰기 순서는 쓰기, `fsync`, `close`, `rename`이다.
     - NFS는 close-to-open 일관성을 따르므로 `close` 전에 `rename`하면 Mailo가 내용을 못 볼 수 있다. 일반 지식에 근거한 추정이며 검증하지 않았다.
     - 보완됨(2026-11-23): 구현 중 확정 21에서 NFSv4 loopback으로 확인했고 이 추정은 재현되지 않았다. 호출처 쓰기 순서는 바꾸지 않는다.
   - 임시 이름은 점(`.`)으로 시작한다. 완성 파일은 `*.json`이다.
   - 완성 파일 이름은 호출처가 고유하게 만든다. 예: UUID.
     - 같은 이름으로 `rename`하면 아직 수집되지 않은 기존 파일을 경고 없이 덮어쓴다. 리뷰어가 ext4에서 확인했다.
     - 덮어쓰기를 막아야 하면 `link`로 최종 이름을 만든 뒤 임시 이름을 `unlink`하는 방식을 쓸 수 있다. 채택 여부는 미확정이다.
   - Mailo는 `*.json`이 아닌 파일과 점으로 시작하는 파일을 무시한다.
   - Mailo는 일정 시간이 지난 점(`.`) 임시 파일을 삭제한다. 호출처는 목록을 볼 수 없어 직접 정리할 수 없기 때문이다. 시간 값은 설정으로 받는다.
   - rename은 같은 폴더 안에서만 한다. 다른 폴더나 파일시스템으로 옮기지 않는다.
4. **Mailo는 폴링으로 수집한다.**
   - 파일 변경 이벤트에 의존하지 않는다.
   - 폴링 간격은 설정으로 받는다.
5. **수집 절차는 검사, 파싱, 큐 등록, 파일 삭제 순서다.**
   1. `O_RDONLY | O_NOFOLLOW | O_NONBLOCK`으로 열고 `fstat`으로 확인한다.
      - 일반 파일이어야 하고 `st_nlink == 1`이어야 한다.
      - `lstat` 뒤에 `open`하는 순서는 쓰지 않는다. 그 사이에 파일이 바뀔 수 있다.
      - 이름이 `*.json`인 FIFO를 일반 `open`으로 열면 폴러가 멈춘다. 리뷰어가 로컬에서 확인했다. `O_NONBLOCK`으로 열면 즉시 반환되고 `fstat`이 일반 파일이 아님을 알려 준다.
   2. 크기 상한을 확인한다. 읽기는 상한 + 1바이트까지만 한다.
      - 호출처가 `rename` 뒤에도 파일을 열어 두고 추가로 쓸 수 있으므로 `fstat` 크기만 믿지 않는다.
   3. 파싱하고 스키마를 검증한다. 대체됨: ADR-0008 결정 3.
   4. 서명이 설정돼 있으면 검증한다. 대체됨: ADR-0008 결정 3.
   5. 봉투 암호화 파일이면 복호화한다. 대체됨: ADR-0008 결정 3.
   6. ADR-0002의 등록 경로로 큐에 등록한다. 대체됨: ADR-0008 결정 3.
   7. DB 커밋이 끝난 뒤 원본 파일을 삭제한다.
   - 3~6단계는 ADR-0008 결정 3의 순서가 대체한다. JWS 구조 파싱, 서명 검증, payload 파싱과 스키마 검증, 복호화, 복호화한 제목·본문의 입력 검증(RQ-030), 지문 계산(ADR-0005), 등록 순서다. 제목이 암호화돼 있으면 CR/LF 헤더 인젝션 검사를 복호화 전에 할 수 없기 때문이다.
   - 거부 기록의 커밋 뒤에 원본을 삭제한다(ADR-0006 결정 3).
6. **중복 수집은 `Idempotency-Key`로 막는다. 파일 채널에서 Key는 필수다.**
   - 큐 등록과 파일 삭제 사이에 Mailo가 종료돼도, 다시 수집한 파일은 같은 Key로 걸러진다.
   - Mailo 인스턴스가 여럿이어서 같은 파일을 동시에 읽어도 같은 Key가 하나만 등록한다.
   - 이미 삭제된 파일의 삭제 실패(파일 없음)는 오류로 보지 않는다.
7. **검증에 실패한 파일은 `rejected/<caller>/`로 옮긴다.** 대체됨: ADR-0006 결정 3·4. 거부 파일은 `rejected/`로 옮기지 않는다. 원본을 삭제하고 거부 기록과 `INTAKE_REJECTED` 이벤트를 DB에 쓴다.
   - 대상은 형식 오류, 크기 초과, 서명 불일치, 복호화 실패 파일이다. ADR-0006 결정 3은 Key 누락, 지문 불일치, 입력 검증 실패(RQ-030), 첨부 포함 요청, JWS·JWE의 caller 불일치, `iat` 범위 위반, Key 형식 위반(ADR-0005·0008)을 추가한다.
   - 사유는 별도 기록으로 남긴다. 로그와 사유에 본문을 남기지 않는다.
   - 격리 폴더는 Mailo만 읽는다. 대체됨: ADR-0006 결정 4(`rejected/` 폐지).
8. **호출처 식별과 접근 통제는 폴더로 한다.**
   - `<caller>` 폴더 이름이 `caller_id`다. ADR-0002의 `(caller_id, idempotency_key)`에 쓴다.
   - Mailo는 설정에 등록된 호출처 폴더만 수집한다. 등록되지 않은 폴더는 무시한다.
   - 호출처 계정은 자기 `inbox/<caller>/`에 파일을 만들 수 있다.
   - 호출처 계정은 자기 폴더의 목록 조회, 다른 호출처 폴더, `rejected/`에 접근할 수 없다. `rejected/`는 폐지됐다(ADR-0006 결정 4). 앞의 두 규칙은 유지한다.
   - 호출처는 자기가 만든 파일의 소유자이므로 그 파일을 읽거나 삭제하는 것은 막을 수 없다. 권한 모드와 sticky bit로도 막을 수 없다. 리뷰어가 로컬에서 확인했다.
   - Mailo가 호출처 소유 파일을 읽으려면 공용 그룹과 setgid 디렉터리, 또는 default ACL을 쓴다. 호출처 umask에 의존하지 않는다.
   - 보완됨(2026-11-23, 구현 중 확정 28): 권장은 default ACL이다. 공용 그룹 + setgid는 ACL을 쓸 수 없는 파일시스템용 대안이고 호출처 umask `027` 이하 요건이 있다(umask `077`에서 Mailo가 읽지 못한다). 위 "호출처 umask에 의존하지 않는다"는 default ACL에서만 성립한다. 호출처가 생성 mode `0600`으로 만든 파일은 두 방식 모두 수집되지 않고 `unreadable`로 남는다(호출처가 `rename` 전에 `0660`으로 `chmod`해야 한다).
   - 같은 호스트 Docker 볼륨에서는 Mailo와 호출처 컨테이너가 서로 다른 non-root UID로 실행돼야 한다. 둘 다 root이면 권한 모델이 성립하지 않는다.
   - `rejected/`로의 이동은 `inbox/`와 같은 파일시스템에서 한다. 대체됨: ADR-0006 결정 4. 이동이 없으므로 이 조건은 필요 없다.
   - 폴더·파일 모드와 계정 구성은 운영 문서에서 정한다.
9. **호출처별 서명(HMAC) 검증을 설정으로 지정한다.** 대체됨: ADR-0008 결정 2. 서명은 JWS(HS256)다. `required`·`none` 명시, 호출처별 비밀키, 같은 규칙의 두 환경 적용, NAS/NFS에서 `required` 권장은 유지한다.
   - 서명은 파일 내용 위조를 막는다. 폴더 쓰기 권한이 뚫려도 서명 없는 파일은 거부한다.
   - 호출처마다 비밀키가 다르다.
   - 호출처를 등록할 때 서명 사용 여부(`required` 또는 `none`)를 명시해야 한다. 기본값은 없다.
   - 같은 호스트 볼륨과 NAS/NFS 폴더 모두 같은 코드와 같은 규칙으로 동작한다.
   - 운영 문서는 NAS/NFS 폴더에 `required`를 권한다.
10. **두 환경(같은 호스트 볼륨, NAS/NFS)을 모두 검증 대상으로 한다.**
    - 구현 시 두 환경에서 수집 동작을 각각 통합 테스트로 확인한다.

## 검토한 대안

| 대안                          | 채택하지 않은 이유                                                                          |
| ----------------------------- | ------------------------------------------------------------------------------------------- |
| `processing/`, `done/` 폴더   | 이동 단계가 늘고 평문 본문이 폴더에 남는다. Key 중복 방지가 있어 이동 없이 삭제해도 안전하다 |
| 파일 변경 이벤트(inotify 등)  | NAS/NFS에서 이벤트가 전달되지 않을 수 있다                                                  |
| 파일명에서 Key 유도           | 호출처가 파일명을 바꿔 같은 요청을 다른 Key로 보낼 수 있다. 내용 안의 Key를 기준으로 한다   |

## 결과

- RQ-002의 수집 규칙과 RQ-024의 접근 통제 방향이 정해진다.
- 이 ADR 작성 시점에는 파일 채널에서만 Key가 필수였다. ADR-0005 결정 1이 REST까지 필수로 확대했다(RQ-001·RQ-011).
- 수집한 파일은 큐 등록 직후 삭제하고 파일 채널은 작업 ID를 돌려주지 않는다. 호출처는 Key로 작업을 조회해야 한다(ADR-0006 결정 1). 이 조회에는 REST 자격이 필요하다(ADR-0006 결정 5).
- NFS는 클라이언트 캐시 때문에 방금 rename된 파일이 늦게 보일 수 있다. 이 경우 수집이 폴링 간격보다 늦어질 수 있다. 일반 지식에 근거한 추정이며 검증하지 않았다. 보완됨(2026-11-23): 구현 중 확정 21에서 기존 폴더에서는 재현되지 않았고, 폴러의 첫 폴링 뒤에 만든 새 호출처 폴더에서만 31초 지연이 확인됐다.
- rename 원자성과 폴링 동작은 이 세션에서 NFS에 대해 검증하지 않았다. 구현 시 두 환경에서 확인한다. 보완됨(2026-11-23): 구현 중 확정 20~27에서 같은 호스트 loopback으로 확인했다. 실제 NAS는 검증하지 않았다.
- 위 규칙은 2026-11-23에 구현됐다(상태 절 참조). 이 절의 다른 문장은 작성 시점의 서술이다.

## 미확정

- 공통 스키마의 필드명. 수신자·발신자 필드(CC, BCC, From, Reply-To)는 요청에 포함하고 ADR-0005 결정 3의 지문 입력 범위에 든다.
- 결정됨: 봉투 암호화 암호문 형식과 알고리즘은 ADR-0008 결정 1이 JWE(`RSA-OAEP-256`, `A256GCM`)로 정했다.
- 파일 크기 상한은 원시 요청 2 MiB로 정했다(RQ-030). 폴링 간격과 임시 파일 정리 시간의 기본값은 미결정이다. 결정됨(구현 중 확정): 폴링 30초, 임시 파일 정리 1시간(둘 다 추정).
- `link` 방식으로 덮어쓰기를 막을지 여부. 미결정으로 남는다. 구현은 막지 못한다(구현 중 확정 10).
- 해소됨: `rejected/` 보존 기간과 사유 기록 형식은 필요 없다. ADR-0006 결정 4가 폴더를 폐지했고, 거부 기록과 이벤트의 보존 기간은 30일이다(ADR-0006 결정 8).
- 호출처 계정·폴더 모드 구성. 운영 문서에서 정한다.
  - 결정됨(구현 중 확정 14~16, 같은 호스트 Docker 볼륨 한정): default ACL 방식을 권장하고 공용 그룹 + setgid는 대안이다. NAS/NFS의 계정·폴더 모드는 미확정이다.
- NAS/NFS 권장 mount 옵션(속성·목록 캐시). 운영 문서에 적는다.
  - 결정됨(구현 중 확정 22): `vers=4.2,sec=sys,hard,lookupcache=pos`. 근거와 한계는 `docs/operations/nfs.md`.
- 결정됨: NFS 통합 테스트는 3단계에서 Linux VM(CI 러너 포함)의 `nfs-kernel-server`를 같은 호스트에 NFSv4.1 loopback mount해 `root_squash`와 non-root UID 2개로 실행한다. WSL 로컬에서는 건너뛴다. CI 러너에서 mount가 되는지는 검증하지 않았다(RQ-002·RQ-024 수용 조건 참조).
  - 실행됨(구현 중 확정 20): WSL2에서도 커널 nfsd 모듈이 있어 건너뛰지 않고 실행했다. CI 러너는 여전히 검증하지 않았다.
- 결정됨: 첨부파일은 1·2단계에서 지원하지 않는다. `attachments` 필드가 있는 파일은 수집 거부로 처리한다. 필요해지면 별도 ADR로 정한다.

## 구현 중 확정 (2026-11-23)

결정 문구는 바꾸지 않는다. 구현이 정한 세부와 추정과 다른 점은 다음과 같다. 코드는 `apps/mailo/src/file-channel`, 설정은 `config`에 있다.

1. **활성 조건과 수명 주기.** `MAILO_FILE_CHANNEL_ROOT`(절대 경로)가 있을 때만 폴러가 켜진다. 기본은 꺼짐이다.
   - 호출처 레지스트리에서 `fileChannel: true`인 호출처의 `<root>/inbox/<caller_id>/`만 수집한다. `fileChannel: false`이거나 등록되지 않은 폴더는 읽지도 않고 거부 기록도 만들지 않는다.
   - 앱 기동 때 폴러를 Worker보다 먼저 시작한다. root가 읽을 수 있는 디렉터리가 아니면 `FileChannelStartError`로 기동하지 않는다.
   - 종료 순서는 HTTP 서버 닫기, 폴러 정지, Worker drain, DB 풀 닫기다. 폴러 정지는 새 파일을 시작하지 않고 진행 중인 파일의 등록·삭제를 끝낸 뒤 끝난다.
   - 코드는 폴더를 만들거나 chmod하지 않는다. inbox가 없으면 호출처별로 한 번만 경고 로그를 남기고 건너뛴다.
2. **설정과 기본값(모두 추정).** `MAILO_FILE_POLL_INTERVAL_MS`(30000, 간격은 ±10%로 흩뿌린다), `MAILO_FILE_MAX_BYTES`(기본은 `MAILO_MAX_REQUEST_BYTES`와 같은 2 MiB), `MAILO_FILE_TEMP_MAX_AGE_SECONDS`(3600), `MAILO_FILE_BATCH_PER_CALLER`(100).
   - 시간 단위를 ms로 둔 것은 `MAILO_WORKER_POLL_MS`와 맞추고 테스트가 짧은 간격을 쓰기 위해서다.
3. **읽기와 판정(결정 5의 1~2단계).** `O_RDONLY | O_NOFOLLOW | O_NONBLOCK`으로 열고 `fstat`으로 일반 파일, `nlink == 1`을 확인한다. 읽기는 상한 + 1바이트까지다.
   - 심볼릭 링크(`ELOOP`), FIFO·소켓·디렉터리, 하드링크는 내용을 읽지 않고 거부한다. 하드링크를 읽으면 다른 파일의 내용을 해시로 추측하는 통로가 된다.
   - 읽기 권한이 없는 파일(`EACCES`·`EPERM`)은 거부하지 않고 남긴다. 호출처 파일을 Mailo가 읽게 하는 권한 구성이 틀렸을 때 유효한 요청이 삭제되는 것을 막기 위해서다. 폴링 요약 로그의 `unreadable`로 드러난다. 추정과 다른 점: 문서에는 이 경우의 규정이 없었다.
   - 확장자 판정은 대소문자를 구분한다(`*.json`만). UTF-8로 읽을 수 없는 파일 이름(U+FFFD 포함)은 같은 바이트로 다시 열 수 없어 수집하지 않고 요약 로그의 `badNames`로 센다. 이름이 `.json`으로 끝나는 디렉터리는 건너뛴다.
4. **거부 기록의 sha256과 크기(ADR-0006 결정 3의 "파일 전체 sha256"을 구체화).**
   - 끝까지 읽은 파일: 파일 전체의 sha256과 실제 크기.
   - 크기 초과 파일: 처음 `상한 + 1`바이트의 sha256, 크기는 열 때의 `fstat` 크기(읽은 양보다 작지 않게)다. 파일 전체를 해시하면 계속 커지는 파일이나 매우 큰 파일에서 폴러가 오래 붙잡힌다. 읽기 양이 정확히 정해져 있어 청크 크기와 무관하게 같은 값이 나오므로 `(caller_id, 파일 이름, sha256)` 멱등성이 유지된다. 한계: 이 sha256은 호출처가 계산하는 전체 파일 해시와 일치하지 않는다. 앞 `상한 + 1`바이트와 이름이 같은 서로 다른 큰 파일은 한 기록으로 합쳐진다.
   - 내용을 읽지 않은 파일(심볼릭 링크, FIFO, 하드링크 등): 빈 입력의 sha256(`e3b0c442...`)과 크기 0이다. 한계: 같은 이름의 심볼릭 링크를 다시 만들면 새 거부 기록과 이벤트가 생기지 않는다. 원본은 삭제된다.
5. **거부 사유 코드.** `openRequest` 실패는 `toRejectionReason`을 그대로 쓴다. 크기 초과는 `SIZE_EXCEEDED`, 같은 Key의 다른 내용은 `FINGERPRINT_MISMATCH`다. 일반 파일이 아닌 항목(심볼릭 링크·FIFO·하드링크 등)은 계약의 사유 코드 11종에 맞는 값이 없어 `MALFORMED`로 기록한다. 코드를 늘리지 않았다(계약 변경이 필요하다).
6. **거부 기록의 Key.** 호출처가 Key로 거부를 찾을 수 있도록 파싱한 `idempotencyKey`를 기록한다(ADR-0006 결정 1). `openRequest`의 실패 결과에는 Key가 없어서 `file-channel/key-hint.ts`가 파일에서 따로 꺼낸다.
   - 서명 `none`: 최상위의 `idempotencyKey`. 서명 `required`: 서명 검증이 끝난 뒤의 사유(`VALIDATION_FAILED`, `IAT_OUT_OF_RANGE` 등)일 때만 `payload` 안의 값. `MALFORMED`·`SIGNATURE_*`일 때는 위조일 수 있어 null이다.
   - Key 형식(ADR-0005 결정 1)을 지키지 않으면 null이다. Key는 로그에 남기지 않는다.
7. **삭제(결정 5의 7, 결정 6).** 등록 또는 거부 기록이 커밋된 뒤에만 지운다.
   - 지우기 직전에 `lstat`의 `dev`·`ino`가 처음 읽은 파일과 같은지 확인한다. 호출처가 읽은 뒤 같은 이름으로 새 파일을 rename해 덮었다면 읽은 적 없는 그 파일을 지우지 않고 다음 폴링이 수집한다. 확인과 `unlink` 사이의 짧은 틈은 남는다.
   - 이미 없으면(`ENOENT`) 오류가 아니다. 삭제 실패(권한 등)도 오류로 세지 않고 `deleteFailed`로 센다. 파일이 남아 다시 수집돼도 같은 Key(등록) 또는 같은 `(caller_id, 파일 이름, sha256)`(거부)로 걸러진다.
8. **공정성.** 한 폴링은 호출처마다 최대 `batchPerCaller`개를 처리하고 다음 호출처로 넘어간다. 상한에 걸려 파일이 남았고 이번 폴링이 한 건이라도 정리했으면 간격 없이 바로 다음 폴링을 한다. 정리한 것이 없으면(삭제 실패, 읽기 권한 없음) 정상 간격을 기다린다.
   - 한계: 같은 폴더에서 삭제할 수 없는 파일이 상한 개수 이상 쌓이면 그 호출처의 뒤쪽 파일이 처리되지 않는다. 다른 호출처에는 영향이 없다. 폴더 안 순서는 `readdir` 순서다.
     - 보완됨(2026-11-23, 구현 중 확정 29): 위 한계는 한 폴링이 모으는 이름 수 한도(`batchPerCaller`의 100배, 최대 100000)까지 완화됐다.
   - 파일과 무관한 오류(DB 장애 등)가 3번 연달아 나면 그 폴링을 접고 다음 간격에 다시 시도한다.
     - 보완됨(2026-11-23, 구현 중 확정 29): 폴더 목록 읽기 실패(`EACCES` 등)는 이 연속 오류에 세지 않는다.
9. **임시 파일 정리(결정 3).** 점(.)으로 시작하는 항목 중 디렉터리가 아닌 것을 `lstat` mtime이 `MAILO_FILE_TEMP_MAX_AGE_SECONDS`보다 오래되면 지운다(심볼릭 링크는 링크 자체만). 나이는 파일 mtime과 Mailo 시계의 차이이므로 NFS 서버와 시계가 어긋나면 오차가 난다. 느리게 쓰는 파일의 mtime은 쓸 때마다 갱신되지만, 정리 시간보다 오래 쓰기를 멈춘 임시 파일은 지워질 수 있다.
10. **덮어쓰기.** `link` 방식은 채택하지 않았다. 호출처가 같은 이름으로 rename하면 아직 수집되지 않은 기존 파일이 사라지는 것을 폴러는 막을 수 없다. 완성 파일 이름은 호출처가 고유하게 만들어야 한다(결정 3).
11. **헬스.** `/health` 계약(openapi)은 바꾸지 않았다. 폴러는 마지막 폴링 시각·성공 여부·처리 대상 호출처 수를 내부 상태(`status()`)로 갖고, 파일이 처리된 폴링마다 호출처별 요약(등록·중복·거부·삭제 실패 건수)을 한 줄 JSON 로그로 남긴다. 외부에서 폴러가 멈췄는지 확인하는 신호는 아직 없다.
12. **검증 범위(결정 10).** 통합 테스트는 WSL2 로컬 파일시스템의 임시 디렉터리와 PostgreSQL 17에서 실행했다. 확인한 것: 정상·서명·JWE 수집, 임시 이름·비json 무시, FIFO·심볼릭 링크·하드링크·크기 상한, 종료 뒤 재수집, 두 폴러 동시 수집, 거부 기록 멱등, 호출처 분리, 배치 상한, 종료 시 진행 중 파일 완료, 파일에서 Worker와 SMTP까지의 e2e. 확인하지 않은 것: NAS/NFS의 rename 가시성·`close` 전 `rename`·캐시 지연, Docker 볼륨 마운트, 공용 그룹·setgid·ACL로 Mailo가 호출처 파일을 읽는 구성, 호출처 계정의 목록 조회·다른 폴더 접근 차단. 실제 SIGTERM 수신 상태의 프로세스는 실행하지 않았고 폴러 `stop()`과 앱 종료 훅만 확인했다.

## 구현 중 확정: 같은 호스트 Docker 볼륨 권한 (2026-11-23, 3단계)

결정 문구는 바꾸지 않는다. 결정 8의 "계정 구성, 폴더·파일 모드는 운영 문서에서 정한다"를 이 절이 정한다. 재현 스크립트는 `scripts/volume/`, 보조 파일은 `test/volume/`, 구성 예시는 `docker-compose.volume-example.yml`이다.

13. **검증 환경과 범위.** Docker 29.8.0, Compose v5.5.1, WSL2 호스트의 ext4 위 local 드라이버 named volume이다. Mailo 이미지는 저장소 `Dockerfile`로 빌드했다. 호출처 역할 컨테이너는 `node:24.20.0-alpine` + `acl`이다.
    - 확인한 것: named volume 하나를 Mailo(UID 1000), 호출처 B(UID 10002), 호출처 C(UID 10003)가 공유하는 구성. 두 방식(default ACL, 공용 그룹 + setgid)의 비교, root·같은 UID 사례, rename 원자성(4 MiB × 100건), 실제 Mailo 컨테이너 e2e(파일 → 폴링 → 발송 → 삭제).
    - 확인하지 않은 것: bind mount, Docker Desktop·macOS·Windows 파일 공유, rootless Docker, `userns-remap`, NFS(별도 작업), ext4 외 파일시스템의 ACL 지원, 폴러의 임시 파일 정리 코드(같은 디렉터리 쓰기 권한으로 0600 파일이 삭제되는 것만 확인했다), 실제 SIGTERM 종료.
14. **권장 구성은 default ACL이다.** 계정은 Mailo 1개와 호출처마다 1개이고 모두 non-root, UID는 서로 다르다. 공용 그룹은 필요 없다. `scripts/volume/init-volume.sh acl <루트>`가 아래 상태를 만든다.

    | 경로 | 소유 | 모드·ACL |
    | --- | --- | --- |
    | `<root>`, `<root>/inbox` | root | `0755`, `0711`(통과만 허용, 호출처 이름 목록을 숨긴다) |
    | `<root>/inbox/<caller>/` | Mailo UID | `0700` + `user:<호출처 UID>:-wx` + default ACL `user::rw-, user:<Mailo UID>:rw-, group::---, mask::rw-, other::---` |

    - 폴더 소유자가 Mailo이므로 호출처는 폴더 `chmod`·`setfacl`을 할 수 없다.
    - 호출처가 만든 파일은 default ACL로 Mailo에게 `rw-`가 붙고 호출처 umask는 적용되지 않는다.
    - compose에서 호출처는 `volume.subpath: inbox/<caller>`로 자기 폴더만 마운트한다. 권한 모델과 별개의 이중 방어이고, 권한 검증은 전체 볼륨을 마운트해 수행했다.
15. **두 방식 비교(같은 28개 확인 항목 기준).**

    | 항목 | default ACL | 공용 그룹 + setgid(`2370`, 소유자 호출처, 그룹 공용 G) |
    | --- | --- | --- |
    | 호출처 umask 077 파일을 Mailo가 읽음 | 읽음 | 못 읽음 |
    | 호출처가 mode 0600으로 생성한 파일을 Mailo가 읽음 | 못 읽음 | 못 읽음 |
    | 호출처가 자기 폴더 권한 변경(`chmod u+r`) | 불가 | 가능(자기 폴더 한정, 목록 조회 금지를 호출처가 해제) |
    | 필요 조건 | 파일시스템 ACL 지원, 이미지에 `setfacl`(init 컨테이너만) | 없음(POSIX 모드만) |
    | 폴더 소유자 | Mailo | 호출처 |

    - 권장 이유: umask 의존이 없고 호출처가 폴더 권한을 바꿀 수 없다. 그룹 방식은 두 점에서 ACL 방식보다 약하다.
    - 그룹 방식은 파일시스템이 ACL을 지원하지 않을 때의 대안이다. 이 경우 호출처 umask를 `027` 이하(그룹 읽기 허용)로 고정해야 한다. `init-volume.sh group`이 이 모드를 만든다.
16. **호출처 쓰기 규약(추가).** 결정 3의 순서(임시 이름 쓰기, `fsync`, `close`, `rename`)에 더한다.
    - 임시 파일을 mode `0600`으로 만드는 도구(`mkstemp`류)를 쓰면 두 방식 모두 Mailo가 읽지 못한다. `rename` 전에 `fchmod 0660`을 한다. 그렇지 않으면 파일은 삭제되지 않고 남으며 폴링 요약 로그의 `unreadable`로 드러난다(e2e로 확인).
    - 파일을 `0666`으로 만들면(Node `writeFileSync` 기본, 셸 리다이렉트) default ACL 방식에서는 umask와 무관하게 읽힌다.
17. **확인 결과.** 항목별 스크립트를 1회씩 실행했다. 판정은 기대(허용·차단)와 실제 동작의 비교다.

    | 항목 | 결과 | 근거 |
    | --- | --- | --- |
    | (a) 자기 폴더에 임시 이름으로 쓰고 rename | 성공(두 방식) | `verify-permissions.sh` |
    | (b) Mailo가 호출처 소유 파일을 읽고 삭제 | ACL 성공, 그룹은 umask 077에서 읽기 실패. 두 방식 모두 mode 0600 생성 파일은 읽기 실패(삭제는 가능) | 같은 스크립트 |
    | (c) B가 C 폴더에 접근(목록·읽기·생성·rename·삭제), inbox 루트 목록 | 모두 차단(두 방식) | 같은 스크립트 |

    - e2e의 첫 실행은 스크립트 오류로 4건이 어긋났다(SMTP 로그의 `Subject`가 MIME 인코딩돼 한글 제목 검색이 실패). 제품 동작 문제가 아니며 제목을 ASCII로 바꿔 다시 실행했다.
18. **문서와 어긋난 점.**
    - 결정 8과 RQ-024는 "공용 그룹과 setgid 또는 default ACL로 읽는다. 호출처 umask에 의존하지 않는다"고 쓴다. 공용 그룹 + setgid는 umask에 의존한다(077에서 실패). umask 독립은 default ACL에서만 성립한다.

    - 결정 8의 "호출처 계정은 자기 폴더의 목록 조회를 할 수 없다"는 성립한다. 그룹 방식에서는 폴더 소유자인 호출처가 모드를 바꿔 해제할 수 있다.
    - 위 항목에 대한 결정 문구·RQ 요구사항 문구 변경은 하지 않았다. 변경 여부는 사용자 결정이다. 처리됨(2026-11-23): 사용자 위임 결정으로 확정 28이 결정 8과 RQ-024에 "보완됨" 표기를 달았다.

## 구현 중 확정: NAS/NFS (2026-11-23, 3단계)

결정 문구는 바꾸지 않는다. 결정 3·10과 결과 절의 NFS 추정을 실측으로 갱신한다. 운영 지침과 수치 전체는 `docs/operations/nfs.md`, 재현은 `apps/mailo/scripts/nfs/`, 테스트는 `apps/mailo/test/nfs/`(`pnpm test:nfs`)다.

20. **검증 환경과 범위.** WSL2 커널 6.6.114.1에서 `nfs-kernel-server` 2.6.1을 같은 호스트에 두고 loopback mount했다(`rw,sync,root_squash,no_subtree_check`, 백업 ext4). 호출처(`w`)와 Mailo 인스턴스 둘(`m1`·`m2`)을 서로 다른 주소(127.0.0.1~3)·호스트 이름으로 mount해 별개 NFS 클라이언트로 동작시켰다. 호출처 UID 2001·2002, Mailo는 UID 1000이다. 통합 테스트 31건을 NFSv4.1 기본값과 `MAILO_NFS_VERS=4.2` 기본값으로 각각 실행해 모두 통과했다.
    - 확인하지 않은 것: 실제 NAS 제품, 네트워크 지연·장애, 서버 재시작·failover, NFSv3·4.0, Kerberos, `all_squash`, 호스트 간 UID 불일치, 시계 어긋남, Windows·macOS 클라이언트, CI 러너.
21. **추정과 다른 점.**
    - 결정 3의 "`close` 전에 `rename`하면 Mailo가 내용을 못 볼 수 있다"는 재현되지 않았다. 쓰기만, `fsync`만, `close` 후 세 경우 모두 Mailo가 1 MiB 전체를 읽었다(3 MiB·delegation 없음은 수동 실험). 이 환경의 Linux 클라이언트가 `rename` 때 쓰기 대기 데이터를 서버에 보내는 것으로 보이며(추정), 다른 클라이언트에서도 같다고 단정하지 않는다. 호출처 규약(쓰기, `fsync`, `close`, `rename`)은 바꾸지 않는다. `rename` 뒤에 덧쓴 부분은 `close` 전에 보이지 않아 부분 파일이 노출된다(524293 / 1048586 바이트).
    - 결과 절의 "방금 rename된 파일이 늦게 보일 수 있다"는 기존 폴더에서는 재현되지 않았다. 6개 mount 옵션(기본값, `actimeo=60`, `lookupcache=none`·`pos`, `noac`, `nocto,actimeo=60`) 모두 다음 폴링에서 7~13 ms에 보였다. `opendir`가 폴더 속성을 다시 확인하는 것으로 보인다(추정).
    - 지연이 생기는 곳은 호출처 폴더가 Mailo의 첫 폴링 뒤에 만들어지는 경우다. "없음" 조회 결과가 캐시되어 기본값에서 31.3초 뒤에 보였다. `acdirmin=acdirmax=3`은 3.0초, `lookupcache=pos`는 8~9 ms다.
22. **권장 mount 옵션.** `vers=4.2,sec=sys,hard,lookupcache=pos`. 호출처 호스트도 `vers=4.2`다. 이유: `lookupcache=pos`는 위 새 폴더 지연을 없앤다. 4.2는 default ACL 폴더에서 호출처 umask 077인 파일을 Mailo가 읽게 한다(4.1은 `unreadable`로 남는다, 서버가 ACL mask를 `---`로 만든다). `nocto`는 close-to-open 보장을 버리므로 쓰지 않는다(이 환경에서는 영향이 없었으나 추정으로 금지). `actimeo`는 영향이 없어 기본값을 둔다.
23. **권한 모델(결정 8).** 구현 중 확정 14의 default ACL 모델이 NFS에서도 성립한다. 호출처 UID는 자기 폴더에 만들 수 있고 폴더·`inbox` 목록 조회, 폴더 `chmod`, 다른 호출처 폴더의 만들기·목록·읽기·삭제가 모두 `EACCES`다. root는 `root_squash`로 거부된다. 공용 그룹 + setgid 대안은 호출처 umask(027 읽힘, 077 거부)에 달렸고, 서버가 보조 그룹을 클라이언트 값 대신 서버 조회(`--manage-gids`)로 판정하면 보조 그룹만 가진 계정은 거부된다.
24. **`ESTALE` 결함과 수정.** 다른 클라이언트가 지운 파일을 지운 직후 열면 `open`은 되고 `fstat`·`read`가 `ESTALE`(errno 116)로 실패하는 경우가 있었다(시도의 약 5~50%). Node(libuv)는 `ESTALE` 이름이 없어 `error.code`가 `"Unknown system error -116"`이고 `errno`가 `-116`이다. 수정 전에는 `readInboxFile`이 40회 중 8회 이 오류를 던졌고 폴링 오류로 세어졌다. 수정: `file-channel/errno.ts`의 `isStale`(errno 판별)을 쓰고, `open`·`fstat`·`read`·`lstat`·`unlink`의 `ESTALE`은 파일이 없는 것과 같게(`gone`) 처리한다. `opendir`·`readdir`의 `ESTALE`은 한 번 다시 읽고, 다시 실패하면 그 호출처를 이번 폴링에서 건너뛰며 `file_inbox_stale` 경고를 남긴다. 단위 테스트(`test/file-channel/errno.spec.ts`)와 NFS 테스트(40회 반복, 오류 0건 단언)로 고정했다.
25. **동시 수집(결정 6).** 서로 다른 NFS 클라이언트의 두 폴러가 같은 폴더를 3라운드(라운드당 20건) 동시에 읽어 작업 60건, Key 중복 0, 오류 0, 파일 잔존 0이었다. 한 폴러가 다른 폴러가 지운 파일을 만나는 `gone`이 라운드마다 수 건 생겼다. 수정 전에는 한 실행에서 오류 1건이 났다(원인 로그는 확인하지 않았고 `ESTALE`로 추정).
26. **(d) 파일 종류 검사.** 심볼릭 링크(`O_NOFOLLOW`)·FIFO는 NFS에서도 내용을 읽지 않고 `MALFORMED`로 거부·삭제된다. 하드링크 쌍은 한쪽이 거부되고 나머지는 nlink 1이 되어 수집된다(로컬과 같다). rename 원자성: 2 MiB 파일 16개를 쓰는 동안 반복 읽기에서 부분 내용 0건이다.
27. **재현과 위험.** `apps/mailo/scripts/nfs/run.sh`(환경 준비, 테스트, 정리). 비밀번호 없는 `sudo`가 필요하며 없으면 종료 코드 20으로 중단한다. 위험도 중간: `/etc/exports.d/mailo-nfs-test.exports`와 `/srv/mailo-nfs-test`, loopback mount 3개를 만든다. 롤백은 `apps/mailo/scripts/nfs/teardown.sh`. 기존 `/etc/exports`는 건드리지 않는다. 문서와 어긋난 점: 결정 10의 "각 환경에서 통합 테스트"는 NFS를 실제 NAS가 아닌 loopback으로 충족했다. 실제 NAS 검증은 남는다.

## 구현 중 확정: 권한 문구 보완 (2026-11-23, 3단계 마무리)

결정 문구는 지우지 않는다. 결정 8에 "보완됨" 표기를 달았고 RQ-024의 같은 문구도 같은 방식으로 보완했다. 사용자가 검증 결과에 따른 문구 결정을 위임해 정한 내용이다.

28. **default ACL 권장, 공용 그룹 + setgid는 대안.**
    - 권장은 default ACL이다. 공용 그룹 + setgid는 파일시스템이 POSIX ACL을 지원하지 않을 때의 대안이다.
    - 공용 그룹 + setgid는 호출처 umask를 `027` 이하(그룹 읽기 허용)로 고정해야 한다. `077`이면 Mailo가 읽지 못한다(확정 15, NFS에서도 같다, 확정 23).
    - "호출처 umask에 의존하지 않는다"는 default ACL에서만 성립한다.
    - 호출처가 파일 생성 mode를 `0600`으로 만들면(`mkstemp`류, Java `createTempFile`) 두 방식 모두 Mailo가 읽지 못한다. 이 파일은 수집되지 않고 삭제되지 않으며 폴링 요약 로그의 `unreadable`로 남는다. 호출처가 `rename` 전에 `0660`으로 `chmod`해야 수집된다(확정 16).
    - NFS에서는 호출처 호스트도 `vers=4.2`여야 default ACL 폴더에서 umask `077` 파일이 읽힌다(확정 22). 위 권고는 `docs/operations/nfs.md`와 `docs/operations/caller-onboarding.md`에 적었다.
    - 바뀌지 않는 것: 호출처 폴더 구성(확정 14), 호출처 목록 조회 금지, 폴러 동작(코드 변경 없음).

## 구현 중 확정: 코드 리뷰 반영 (2026-11-23)

결정 문구는 바꾸지 않는다. 독립 코드 리뷰에서 재현된 결함을 고친 내용이다.

29. **공정성 보완(확정 8, 9).** 재현된 결함 둘을 고쳤다.
    - 오류 예산: 연속 오류 수가 파일 수집 성공에서만 0이 됐다. 읽을 수 없는 호출처 폴더(`opendir` `EACCES`)가 연달아 3곳이면 뒤쪽 호출처가 폴링마다 건너뛰어졌다. 지금은 폴더 목록 읽기 실패를 예산에 세지 않고(로그 `file_poll_failed`는 남는다), 오류 없이 끝난 호출처가 연속 오류를 0으로 되돌린다. 예산은 DB 장애처럼 파일과 무관한 오류 판정용이다.
    - 대상 선정: 읽을 수 없는 파일(`unreadable`)이 `batchPerCaller` 슬롯을 채우면 뒤쪽 정상 파일이 굶었다. 지금은 이름을 `batchPerCaller`의 100배(최대 100000)까지 모으고, 정리된(settled) 파일이 `batchPerCaller`건이 될 때까지 순회한다. 읽을 수 없는 파일은 정리된 것으로 세지 않아 슬롯을 쓰지 않는다. 임시 점 파일 수집 한도도 같다.
    - 선택 이유: 이름 상한만 두고 순회하는 방식이 폴더 순서를 바꾸거나 상태를 저장하는 방식보다 단순하고, 기존 `capped`(정리한 것이 있을 때만 즉시 재폴링) 의미를 유지한다.
    - 남는 한계: 읽을 수 없는 파일이 이름 수집 한도(기본 10000개)를 넘는 폴더는 한도 밖 파일이 처리되지 않는다. 매 폴링이 읽을 수 없는 파일을 한 번씩 다시 열어 보므로 오래 남기지 않는다(`troubleshooting.md`의 `unreadable` 절). 같은 크기의 점 임시 파일이 한도를 넘어도 한도 밖 파일은 이번 폴링에서 정리되지 않는다.
30. **결정 3의 `link` 권고와 결정 5의 `nlink == 1` 충돌.** 결정 3은 덮어쓰기를 막으려면 `link`로 최종 이름을 만든 뒤 임시 이름을 `unlink`할 수 있다고 적는다. 그런데 `link` 직후 `unlink` 전에 폴링이 읽으면 최종 이름의 `nlink`가 2라서 결정 5가 `MALFORMED`로 거부하고 최종 이름을 삭제한다. 재현됨: `test/file-channel/poller.integration-spec.ts`의 "link로 게시한 파일은 unlink 전에 폴링되면 거부된다". 호출처의 `unlink`는 그 뒤에 성공하므로 요청이 거부 기록과 `INTAKE_REJECTED` 이벤트만 남기고 사라진다. 코드는 바꾸지 않는다. 결정 3의 `link` 방식은 사용하지 않는다. 호출처는 `rename`만 쓰고 완성 이름을 고유하게 만든다(확정 10). `caller-onboarding.md`에 반영했다.

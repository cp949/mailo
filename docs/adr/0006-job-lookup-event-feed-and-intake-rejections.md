# 호출처는 REST로 작업을 조회하고 종결 이벤트를 pull하며, 파일 수집 거부는 원본 없이 DB에 기록한다

## 상태

승인됨 (2026-11-23)

1단계에서 결정 1(REST 작업 조회), 2(종결 이벤트 피드), 7(cursor), 8의 보존 삭제를 구현했다.
수집 거부 기록 저장소(`mail_intake_rejections`, `INTAKE_REJECTED` 이벤트 쓰기, 멱등 기록)도 구현했다. 이 기록을 만드는 파일 채널은 2단계이므로 1단계 실행 경로에서는 거부 이벤트가 생기지 않는다(결정 3·4는 2단계).
2026-11-23 2단계에서 파일 채널 폴러가 결정 3·4를 구현했다. 거부 기록과 `INTAKE_REJECTED` 이벤트를 한 트랜잭션에 쓰고 원본을 삭제하며, `rejected/` 폴더는 없다. PostgreSQL 통합 테스트와 e2e(파일 거부 → 이벤트 피드 `INTAKE_REJECTED`, Key 조회 404)로 확인했다. sha256·크기 기록 정책과 사유 코드 대응은 ADR-0004 "구현 중 확정"을 따른다.
검증 범위는 PostgreSQL 통합 테스트와 REST 통합 테스트다. 동시 트랜잭션의 커밋 순서 역전 테스트(`test/events/events.integration-spec.ts`)를 통과했다.
피드 지연 메트릭은 이 시점에는 구현하지 않았다. 구현됨(2026-11-23, 1단계 마무리): 인증된 `/health/ready`의 `eventFeed`(`latestEventAt`, `lagSeconds`)로 노출한다(RQ-017).

- 이 ADR의 결정 4가 ADR-0004 결정 2의 `rejected/<caller>/`와 결정 7을 대체한다.
- RQ-017의 상태가 `보류`에서 `미착수`로 바뀐다. 이벤트 피드(pull)로 해소한다.

## 배경

ADR-0004는 수집한 파일을 큐 등록 직후 삭제하고, 결과를 상태 조회로 확인한다고 적었다.
리뷰에서 다음 문제가 확인됐다.

- 파일 채널은 작업 ID를 돌려주지 않는다. RQ-015의 상태 조회는 작업 ID 기준이어서 파일 호출처는 조회할 수 없다.
- 호출처는 `rejected/`를 읽을 수 없다. 형식 오류나 서명 불일치로 거부된 요청이 사용처에서 보이지 않는다.
- outbox relay가 파일 채널로 전달하는 경우, relay는 등록 성공 여부를 확인할 수 없다.
- `rejected/`는 평문 본문을 보존 기간 없이 보관한다. `done/`을 없앤 이유와 같은 문제다.
- RQ-017은 실패 알림 방식을 정하지 못해 보류 상태다.

## 결정

1. **호출처는 REST로 작업을 조회한다.**
   - `GET /jobs/{jobId}`: 작업 ID로 조회한다(RQ-015).
   - `GET /jobs?idempotencyKey=<key>`: Key로 조회한다. 파일 채널 호출처는 이 조회를 쓴다.
   - `caller_id`는 인증 정보에서 얻는다. 다른 호출처의 작업은 조회할 수 없다.
   - Key 조회는 등록된 작업만 반환한다. 수집 거부와 지문 불일치는 작업 조회에 나오지 않는다.
   - 이 둘은 이벤트 피드의 `INTAKE_REJECTED`로만 확인한다. Key 조회가 404이면 호출처는 피드에서 같은 Key를 찾는다.
   - Key 보존 기간이 지나 행이 삭제된 Key도 404다(ADR-0005 결정 7).
2. **종결 이벤트 피드를 pull 방식으로 제공한다.**
   - `GET /events?after=<cursor>&type=<종류>&limit=<개수>`.
   - 이벤트 종류는 `JOB_SENT`, `JOB_FAILED`, `JOB_EXPIRED`, `INTAKE_REJECTED`다.
   - 이벤트에는 이벤트 ID, 작업 ID 또는 거부 기록 ID, Key, 종류, 실패 원인, 시도 횟수, 수신자가 들어간다.
   - `JOB_SENT` 이벤트에는 `rejectedRecipients`도 들어간다(ADR-0007 결정 7).
   - 호출처는 cursor를 저장한다. 같은 이벤트가 다시 올 수 있으므로 이벤트 ID로 멱등하게 처리한다.
   - 호출처는 자기 이벤트만 읽는다.
   - 종결 이벤트는 작업의 종결 전이와 같은 트랜잭션에서 `mail_events`에 쓴다.
     - ADR-0002 주기 sweep의 `EXPIRED` 전이도 포함한다.
     - 거부 이벤트는 거부 기록과 같은 트랜잭션에서 쓴다.
     - 전이만 커밋되고 이벤트가 없으면 at-least-once 피드가 성립하지 않기 때문이다.
   - cursor 형식과 반환 조건은 결정 7을 따른다.
3. **수집 거부는 원본을 삭제하고 DB에 기록한다.**
   - 대상은 형식 오류, 크기 초과, 서명 불일치, 복호화 실패, Key 누락, 지문 불일치(ADR-0005), 입력 검증 실패(RQ-030), 첨부 포함 요청, JWS·JWE의 caller 불일치, `iat` 범위 위반, Key 형식 위반(ADR-0005·0008)이다.
   - 거부 기록은 `mail_intake_rejections` 테이블에 쓴다.
   - 기록 항목은 호출처, 파일 이름, 크기, sha256, 파싱된 Key(가능한 경우), 사유 코드, 시각이다.
   - 본문은 기록하지 않는다.
   - 거부 기록은 `(caller_id, 파일 이름, sha256)`으로 멱등하게 쓴다. 기록 커밋 뒤 원본 삭제 전에 종료돼도 중복 기록이 생기지 않게 하기 위해서다.
   - 같은 정보로 `INTAKE_REJECTED` 이벤트를 만든다.
   - Key를 파싱하지 못한 파일은 파일 이름과 sha256으로 식별한다. 운영 로그와 메트릭에도 남긴다.
4. **`rejected/` 폴더를 두지 않는다.**
   - ADR-0004의 결정 2의 `rejected/<caller>/`와 결정 7을 이 결정으로 대체한다.
5. **파일 채널 호출처도 REST 자격이 필요하다.**
   - 조회와 이벤트 피드를 쓰기 위해서다.
   - 같은 `caller_id`로 REST 자격과 파일 폴더를 발급한다(RQ-028).
6. **실패 알림 방식(RQ-017)은 이벤트 피드로 한다.**
   - webhook과 실패 파일 쓰기는 제공하지 않는다. 필요해지면 별도 ADR로 정한다.
7. **이벤트 cursor는 `(txid, id)` 쌍이다.**
   - 이벤트 행에 `txid xid8 NOT NULL DEFAULT pg_current_xact_id()`를 기록한다. 인덱스는 `(caller_id, txid, id)`다.
   - 피드는 `WHERE caller_id=$1 AND (txid,id) > ($2,$3) AND txid < pg_snapshot_xmin(pg_current_snapshot()) ORDER BY txid, id LIMIT $4`로 반환한다.
   - cursor는 `(txid, id)`를 base64url로 감싼 불투명 문자열로 준다.
   - 근거: xmin보다 작은 xid의 트랜잭션은 모두 끝났다. 나중에 커밋되는 행이 cursor 앞에 끼어들 수 없다.
   - 단점: DB 어디서든 긴 트랜잭션이 있으면 피드가 멈춘다. 유실은 없다.
   - 필요 버전: PostgreSQL 13 이상.
   - 적용 조건: 전이 트랜잭션에 외부 호출을 넣지 않는다(ADR-0002 결정 9로 성립한다). 피드 지연(now − 최신 반환 이벤트 시각)을 메트릭으로 둔다.
   - 미검증: 구현 때 동시 트랜잭션의 커밋 순서 역전 테스트로 확인한다. compose의 PostgreSQL 이미지가 13 이상인지 확인한다.
8. **이벤트와 거부 기록은 30일 보존한다.**
   - 보존 기간은 추정이다. Key·작업 행 보존 기간(ADR-0005 결정 7)과 같다.
   - 기준 시각은 대상마다 다르다. 작업 행과 Key는 작업 종결 시각, 거부 기록과 `INTAKE_REJECTED` 이벤트는 기록 생성 시각부터 30일이다. 거부에는 종결할 작업이 없기 때문이다.
   - 작업 행을 삭제할 때 그 작업의 이벤트도 함께 삭제한다.
   - 호출처의 권장 폴링 간격은 30초다(추정).

## 검토한 대안

| 대안                    | 채택하지 않은 이유                                                                            |
| ----------------------- | --------------------------------------------------------------------------------------------- |
| webhook                 | webhook 자체의 재시도 큐가 필요하다. 사실상 두 번째 outbox가 생겨 복잡도가 더 크다            |
| 실패 파일 쓰기          | 호출처가 읽을 수 있는 출력 폴더와 권한이 추가로 필요하다. NAS/NFS 환경에서 구성이 늘어난다    |
| 작업 ID 조회만 제공     | 파일 채널 호출처가 작업 ID를 몰라 종결 상태를 놓치고, 수집 거부를 알 수 없다                  |
| `rejected/` 원본 보관   | 평문 본문이 보존 기간 없이 남는다                                                             |
| 원본을 DB 키로 암호화해 짧게 보관 | 원본을 서버에 남기지 않는 결정 3의 목적과 충돌한다. 원본은 호출처가 보유한다           |
| 단일 writer가 번호를 부여 | advisory lock을 잡은 인스턴스가 seq를 주기적으로 매긴다. 리더 선출, 부여 루프, 지연, UPDATE 1회 증가가 생겨 복잡도가 더 크다 |
| `bigserial`을 cursor로 사용 | 동시 트랜잭션의 커밋 순서가 시퀀스 순서와 달라 이벤트를 건너뛸 수 있다(일반 지식, 검증하지 않았다) |

## 결과

- 파일 채널 호출처가 등록 결과와 거부를 Key로 확인할 수 있다.
- 호출처가 이벤트 피드를 폴링해야 한다. 전달 보장은 cursor 저장으로 at-least-once가 된다.
- 운영자는 거부된 파일의 원본을 볼 수 없다. 사유 코드, 크기, sha256으로 호출처와 대조한다.
- `rejected/` 폴더 권한 설계와 보존 정책이 필요 없어진다.
- 피드는 DB의 가장 오래된 열린 트랜잭션이 끝날 때까지 최신 이벤트를 반환하지 못할 수 있다(결정 7).
- PostgreSQL 13 이상이 필요하다.
- sha256은 평문 파일 전체의 해시다. 고유 Key가 들어 있으면 대입 확인 위험은 낮다. Key가 없는 짧은 파일은 예외다.
- 호출처가 30일 넘게 폴링하지 않으면 그 사이의 이벤트를 놓칠 수 있다.
- 결정 1·2·7·8은 통합 테스트로 확인했다. 결정 3·4와 파일 채널 쪽 거부 흐름은 2단계라 구현·검증하지 않았다. 피드 지연 메트릭은 없다. 보완됨(2026-11-23): 결정 3·4는 2단계 파일 채널 폴러가 구현해 통합 테스트로 확인했고(상태 절), 피드 지연 메트릭은 `/health/ready`의 `eventFeed`로 구현했다.

## 미확정

- 결정됨: 이벤트 응답 필드의 형식은 `docs/api/openapi.yaml`이 정했다. `eventId`와 `rejectionId`는 DB의 bigint 식별자를 문자열로 낸다. openapi는 `rejectionId`를 `uuid`로 적어 두었다. 이 불일치는 `docs/api/README.md`의 "계약과 구현의 불일치"에 있다. 해소됨(2026-11-23): 계약을 불투명 문자열로 고쳤다.

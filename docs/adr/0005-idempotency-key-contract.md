# 모든 발송 요청은 Idempotency-Key를 필수로 하고, 같은 Key의 다른 내용은 거부한다

## 상태

승인됨 (2026-11-23)

1단계에서 REST 경로의 결정 1~5, 7, 8을 구현했다. 결정 6(파일 채널 수집 거부)은 2단계에서 파일 채널 폴러가 구현했다(`FINGERPRINT_MISMATCH` 거부 기록, 통합 테스트로 확인).
검증 범위는 PostgreSQL 통합 테스트와 REST 통합 테스트다. 보존 삭제는 SQL 단위로 확인했고 실제 30일 경과는 확인하지 않았다.

- 이 ADR의 결정 4가 ADR-0002 결정 3의 "충돌하면 기존 작업을 조회해 반환한다"를 대체한다.
- RQ-001과 RQ-011의 "Key를 지정할 수 있어야 한다"가 "반드시 지정해야 한다"로 바뀐다.

## 배경

ADR-0001은 Mailo의 보장 범위를 멱등한 요청 등록과 at-least-once 발송으로 정했다.
사용처 relay가 REST로 재호출하는 것이 이 보장의 주 경로다.
리뷰에서 Key 계약이 미완성이라 이 보장이 성립하지 않는다는 지적이 나왔다.

- REST에서 Key가 선택이면, Key 없이 호출한 relay가 응답 타임아웃 뒤 재시도할 때 작업이 중복 등록된다.
  - PostgreSQL unique 제약은 기본 동작에서 NULL끼리 충돌로 보지 않는다. DB도 이를 막지 못한다.
- 같은 Key에 다른 내용이 오면 ADR-0002의 `ON CONFLICT DO NOTHING`은 두 번째 메일을 오류 없이 버린다.
  - 예: 호출처 버그로 Key를 사용자 ID처럼 재사용하는 경우.
- 봉투 암호화는 요청마다 새 키와 IV를 쓰므로 암호문이 매번 다르다.
  - 암호문 해시로 비교하면 정상 재시도도 불일치로 판정된다.
- 평문의 단순 SHA-256 해시를 DB에 저장하면, 짧은 본문은 DB 덤프만으로 대입 확인이 가능하다.
  - RQ-023의 위협 모델에 어긋난다.
- Key 보존 기간이 relay의 최대 재시도 기간보다 짧으면, 그 뒤의 재전달은 중복 발송이 된다.

## 결정

1. **REST와 파일 채널 모두 `Idempotency-Key`를 필수로 한다.**
   - REST는 `Idempotency-Key` 헤더, 파일은 `idempotencyKey` 필드를 쓴다.
   - Key가 없는 요청은 등록하지 않는다. REST는 400으로 응답하고, 파일은 수집 거부로 처리한다(ADR-0006).
   - DB 컬럼은 `NOT NULL`이다.
   - Key는 1~128자이고 허용 문자는 `[A-Za-z0-9._:-]`다(128자는 추정). 형식에 맞지 않으면 REST는 400, 파일은 수집 거부다.
2. **Key의 유일성 범위는 `(caller_id, idempotency_key)`다.**
   - 채널과 무관하게 같은 범위를 쓴다.
3. **같은 Key의 내용 동일 여부는 지문으로 판정한다.**
   - 지문은 `HMAC-SHA256(지문 키, 정규화한 평문 요청 내용)`이다.
   - 평문은 복호화 이후 발송 결과에 영향을 주는 모든 요청 필드다. 암호문은 비교하지 않는다.
     - 수신자(to·cc·bcc), from·replyTo, 제목, text, html, 요청별 정책 필드가 해당한다.
     - 스키마에 필드가 추가되면 지문 범위에도 넣는다.
     - CC나 발신자만 다른 요청이 같은 요청으로 판정되는 것을 막기 위해서다.
   - 지문 키는 Mailo 비밀이며 DB 본문 암호화 키(ADR-0008)와 분리한다.
   - 지문과 함께 `fingerprint_key_version`을 저장한다.
     - 비교는 저장된 버전의 키로 계산한다.
     - 이전 지문 키는 그 버전을 가진 행이 모두 삭제될 때까지 보관한다.
     - 키 교체 뒤 정상 재시도가 409가 되는 것을 막기 위해서다.
   - 정규화 규칙(필드 순서, 수신자 표기)은 설계 문서에서 확정한다.
4. **등록은 `INSERT ... ON CONFLICT (caller_id, idempotency_key) DO NOTHING`으로 처리하고, 충돌하면 지문을 비교한다.**
   - 지문이 같으면 중복 요청이다. 기존 작업을 반환한다.
   - 지문이 다르면 거부한다.
   - 등록 트랜잭션은 READ COMMITTED로 실행한다. 충돌 뒤 기존 행 조회는 별도 문장으로 실행한다.
     - REPEATABLE READ에서는 충돌한 행이 보이지 않거나 직렬화 오류가 날 수 있다(추정, 검증하지 않았다).
5. **REST 응답 계약은 다음과 같다.**

| 상황                        | 응답                         | relay 동작           |
| --------------------------- | ---------------------------- | -------------------- |
| 새 작업 등록                | 202, 작업 ID                 | 완료                 |
| 같은 Key, 같은 내용         | 200, 기존 작업 ID와 상태     | 완료                 |
| 같은 Key, 다른 내용         | 409                          | 재시도하지 않는다    |
| Key 누락, 형식·검증 오류    | 400                          | 재시도하지 않는다    |
| 요청 크기 초과              | 413                          | 재시도하지 않는다    |
| 인증 실패                   | 401                          | 재시도하지 않는다    |
| DB 장애 등 Mailo 내부 오류  | 503                          | 같은 Key로 재시도    |

   - 네트워크 오류와 타임아웃은 relay가 같은 Key로 재시도한다.
   - 4xx 응답은 재시도해도 결과가 같으므로 재시도하지 않는다. 예외는 없다.
   - relay는 409를 영구 실패로 기록하고 운영 알림을 낸다.
   - 호출처별 쿼터를 등록 단계에 두지 않으므로 429는 쓰지 않는다.
6. **파일 채널에서 지문이 다르면 수집 거부로 처리한다.**
   - 거부 기록 방식은 ADR-0006을 따른다.
7. **Key 행은 본문이 삭제된 뒤에도 보존한다.**
   - `mail_jobs` 행은 유지하고 본문 컬럼만 비운다(ADR-0008).
   - 보존 기간은 작업의 종결 시각부터 센다. 종결되지 않은 작업의 Key는 삭제하지 않는다.
   - 기본값은 종결 후 30일이다(추정).
   - 보존 기간은 사용처 relay의 최대 재시도 기간 이상이어야 한다. 최대 재시도 기간은 7일 이하로 한다는 요구를 사용처 연동 문서에 명시한다(7일은 추정).
   - 보존 기간이 지나면 `mail_jobs` 행과 그 행의 `mail_attempts`·이벤트 행을 함께 삭제한다.
   - 삭제 뒤 같은 Key로 다시 오면 새 요청으로 보고, Key 조회(ADR-0006)는 404를 반환한다.
   - 기준 시각은 작업 행·Key가 종결 시각, 거부 기록과 `INTAKE_REJECTED` 이벤트가 기록 생성 시각이다(ADR-0006 결정 8).
   - 보존 기간 순서는 본문 삭제 유예(1일, ADR-0008 결정 7) ≤ 시도·이벤트·거부 기록 보존(30일) = Key·작업 행 보존(30일)이다.
8. **사용처는 Key로 요청 단위의 고유 값을 쓴다.**
   - 예: outbox 행 ID.
   - 사용자 ID처럼 여러 요청이 공유할 수 있는 값은 쓰지 않는다. 쓰면 결정 5의 409가 발생한다.

## 검토한 대안

| 대안                           | 채택하지 않은 이유                                                       |
| ------------------------------ | ------------------------------------------------------------------------ |
| REST에서 Key를 선택으로 유지   | Key 없는 relay 재시도가 중복 등록된다. 채널 간 규칙도 달라진다           |
| 암호문 해시로 내용 비교        | 봉투 암호화 요청은 암호문이 매번 달라 정상 재시도가 불일치가 된다        |
| 평문 SHA-256 해시 저장         | 짧은 본문은 DB 덤프만으로 대입 확인이 가능하다                           |
| 불일치 시 기존 작업 반환       | 두 번째 메일이 오류 없이 사라진다                                        |

## 결과

- RQ-004의 보장이 REST와 파일 모두에서 성립한다.
- 사용처는 요청마다 고유한 Key를 만들어야 한다. outbox 행 ID를 쓰면 추가 비용이 작다.
- `mail_jobs`에 지문과 `fingerprint_key_version` 컬럼이 추가되고 등록 시 비교 한 번이 늘어난다.
- Key 행 보존 기간이 길수록 저장 행이 늘어난다.
- 서명(JWS) 파일은 Key 보존 기간이 지나면 같은 파일을 다시 넣어도 새 요청으로 등록될 수 있다.
  - 서명의 발행 시각(`iat`) 검사로 막는다(ADR-0008 결정 4). 서명이 `none`인 호출처와 REST에는 이 검사가 없다.
- `NULL` 유일성 동작은 PostgreSQL 기본 동작에 대한 일반 지식이며 검증하지 않았다. 구현은 `idempotency_key`를 `NOT NULL`로 두므로 이 동작에 의존하지 않는다.

## 미확정

- 결정됨(구현 중 확정): 정규화 규칙은 `src/crypto/fingerprint.ts`가 정한다.
  - 고정 필드 순서의 JSON에 형식 태그 `mailo-fp-v1`을 붙여 HMAC-SHA256을 계산한다. 규칙을 바꾸면 태그를 올린다.
  - 주소는 앞뒤 공백을 제거하고 도메인만 소문자로 바꾼다. 로컬 파트의 대소문자는 구분한다.
  - 수신자 목록은 목록마다 중복을 제거하고 정렬한다. to와 cc 사이의 중복은 합치지 않는다. 생략과 빈 목록은 같다.
  - `from`·`replyTo`는 생략과 `null`이 같다. `from`을 생략한 요청과 명시한 요청은 다른 내용이다.
  - 제목·text·html은 변환하지 않는다.
- 결정됨: 응답 본문의 필드 구성은 `docs/api/openapi.yaml`이 정했다.

# SMTP 오류를 단계 기준으로 분류하고, 계정 단위 장애는 전역 차단기로 처리한다

## 상태

승인됨 (2026-11-23)

1단계에서 결정 1~9를 구현했다. 결정 10(호출처별 할당)은 2단계 범위이고 2026-11-23에 구현했다("구현 중 확정" 7).
구현 중 확정한 내용은 "구현 중 확정" 절에 모았다. 결정 5(대표 작업 선택)와 결정 9(단계 판별)는 해당 위치에 표기를 달았다.
검증 범위는 로컬 SMTP 서버(smtp-server 3.21.7)와 PostgreSQL 대상 단위·통합 테스트다. 실제 Gmail 서버 대상 검증은 하지 않았다.

- 이 ADR이 ADR-0003의 결정 1~4와 7을 대체한다. ADR-0003의 결정 5·6·8은 유지한다.
- ADR-0003의 결정 2·3(코드 계열 규칙, 매핑 표)은 이 ADR의 결정 3이 메시지 오류에 한정해 이어받는다.
- 이 ADR의 결정 2·6은 ADR-0002 결정 7의 판정 순서와 주기 sweep에 예외를 둔다.

## 배경

ADR-0003은 오류를 작업 단위로 `TRANSIENT`·`PERMANENT`·`SYSTEM`으로 분류한다.
리뷰에서 계정 단위 장애를 작업 단위로 처리하는 문제가 지적됐다.

- 연결 거부, DNS 실패, TLS 오류, 타임아웃이 `TRANSIENT`여서 작업마다 시도 횟수를 소모한다.
  - Google 쪽이나 네트워크가 1시간 끊기면 큐 전체가 시도 횟수를 소진해 `FAILED`가 된다.
- 일일 한도 초과(`550 5.4.5`)는 계정 전체에 걸린다.
  - 작업을 하나씩 시도해 실패하고 시도 횟수를 소모한다.
  - 만료 시각이 한도 회복 시간보다 짧으면 큐 전체가 `EXPIRED`가 된다.
- 연속 `SYSTEM` 오류 임계값이 프로세스 메모리 기준이면, 인스턴스 N개가 각각 임계값만큼 잘못된 인증을 시도한다.
  - 중지 해제 조건이 없다. 타이머로 해제하면 대기 작업이 한꺼번에 몰린다.
- 인증·구성 문제는 `535` 외의 코드로도 온다. 예: STARTTLS 필요, 앱 비밀번호 필요, 웹 로그인 필요.
  - `550 5.7.1`은 일일 한도뿐 아니라 relay 자격 오류에도 쓰이는 것으로 알려져 있다.
  - 응답 코드와 enhanced status code 조합만으로는 구분하기 어렵다.
  - 이 두 항목은 일반 지식에 근거한 추정이며 Google 문서 원문으로 확인하지 않았다.

## 결정

1. **오류 분류 축을 SMTP 단계로 한다.**
   - 계정 상태 오류: 연결(CONN), TLS(STARTTLS 협상), 인증(AUTH) 단계 실패와 한도 초과.
   - 메시지 오류: `MAIL FROM`, `RCPT`, `DATA` 단계의 응답.
2. **계정 상태 오류는 작업의 시도 횟수에 넣지 않는다.**
   - 점유한 작업은 `RETRY_WAIT`로 되돌리고, `next_attempt_at`을 차단기의 재개 시각으로 둔다.
   - 시도는 `mail_attempts`에 기록하되 분류를 `ACCOUNT`로 표시하고 횟수 계산에서 제외한다.
   - 전역 차단기에 실패를 기록한다.
   - 계정 상태 오류는 ADR-0002 결정 7의 판정 순서에서 1·2를 건너뛰고 3·4만 적용한다.
   - `open_until`이 `expires_at`보다 뒤이면 ADR-0003 결정 6에 따라 즉시 `EXPIRED`로 전이한다.
   - 단, 같은 작업이 차단기를 3회 연 뒤에도 같은 응답을 받으면 `PERMANENT`로 보고 `FAILED`로 전이한다(결정 4, 3회는 추정).
3. **메시지 오류만 작업 단위로 분류한다.**
   - 기본 규칙은 `4xx`가 `TRANSIENT`, `5xx`가 `PERMANENT`다. ADR-0003 결정 2의 코드 계열 규칙을 이어받는다.
   - 코드 계열의 예외를 담은 매핑 표(ADR-0003 결정 3)는 이 범주에만 적용한다.
   - `DATA` 전송 중 타임아웃이나 연결 끊김은 `TRANSIENT`다. 서버의 수락 여부가 불명이므로 중복 발송이 생길 수 있다(RQ-013).
4. **한도 초과는 단계와 무관하게 계정 상태 오류로 분류한다.**
   - 예: `550 5.4.5`, `450 4.2.1`(relay 순간 한도), `421 4.7.0`, `421 4.4.5`.
   - 한도 유형에 따라 차단기 재개 시각을 정한다. 일일 한도는 24시간 rolling이므로 길게 둔다.
     - 일일 한도(`550 5.4.5` 등)는 open 1시간 뒤 `half_open`으로 간다. 24시간 rolling이라 한도가 일부씩 회복되기 때문이다(추정). 결정 5의 상한 규칙에 따라 1시간으로 고정한다.
     - 순간 한도(`421`·`450`)는 open 5분에서 시작한다. 대표 작업이 실패할 때마다 2배로 늘리며 상한은 30분이다(추정).
   - 한도 초과와 relay 자격 오류가 같은 코드를 쓰는 경우는 응답 텍스트 패턴으로 구분한다.
   - 구분할 수 없으면 계정 상태 오류로 분류한다. 안전한 쪽이다.
   - `MAIL FROM` 이후 단계에서 받은 계정 상태 오류는 작업별 `account_trips`로 센다. `account_trips`는 `mail_jobs`의 정수 컬럼이다.
     - 같은 작업이 차단기를 3회 연 뒤에도 같은 응답을 받으면, 그 작업을 `PERMANENT`로 보고 `FAILED`로 전이한다(3회는 추정).
     - `550 5.7.1`이 정책 거부처럼 메시지 단위 거부에도 쓰인다고 알려져 있다(추정). 그런 작업이 `half_open` 대표로 반복 선택되면 차단기가 닫히지 않기 때문이다.
5. **전역 차단기는 DB 행 하나로 인스턴스 간에 공유한다.**
   - 테이블은 `mail_circuit_breaker`다. 키는 SMTP 구성 하나당 한 행이다.
   - 상태는 `closed`, `open`, `half_open`이다. 필드는 재개 시각(`open_until`), `probe_until`, 연속 실패 수, 마지막 사유다.
   - `closed`에서 `open`: 연속 계정 상태 오류가 임계값 3회에 이르거나 한도 초과를 받았을 때(3회는 추정).
   - `open` 동안 Worker는 작업을 점유하지 않는다.
   - `open_until`이 지나면 한 인스턴스가 조건부 UPDATE로 `half_open`과 `probe_until`을 기록하고 대표 작업 한 건을 점유한다.
     - `probe_until`은 작업 lease와 같은 값이다.
     - `probe_until`이 지나도 결과가 없으면 다른 인스턴스가 다시 `half_open`을 가져간다. 점유한 인스턴스가 죽어도 고착되지 않게 하기 위해서다.
     - 대표 작업은 직전에 차단기를 연 작업을 제외하고 고른다. (구현 중 변경: 제외하지 않고 후순위로 둔다. 구현 중 확정 3)
   - 대표 작업이 계정 상태 오류 없이 끝나면 `closed`로 돌아간다. 메시지 오류(`TRANSIENT`·`PERMANENT`)로 끝나도 계정은 정상으로 본다.
   - 대표 작업이 계정 상태 오류로 끝나면 대기 시간을 늘려 `open`으로 돌아간다.
   - open 대기 시간은 사유별 초기값에서 시작해 대표 작업이 실패할 때마다 2배로 늘린다. 상한은 `max(30분, 해당 사유의 초기값)`이다(모두 추정).
     - 일일 한도: 초기값 1시간이 상한 30분보다 크므로 1시간 고정이다.
     - 순간 한도: 5분에서 30분까지다.
     - 그 밖의 계정 오류(연결·TLS·인증): 1분에서 30분까지다.
   - 연속 실패 수의 증가와 초기화는 `UPDATE ... RETURNING` 한 문장으로 한다. 연속 실패 수를 프로세스 메모리에 두지 않는다.
   - 차단기 상태(`open`·`half_open`), `open_until`, 마지막 사유를 헬스 응답(RQ-031)과 로그에 드러낸다. ADR-0003 결정 4를 대체하면서 빠진 문장을 복원한 것이다.
6. **차단 중 만료 시각에 이른 작업은 `EXPIRED`로 전이한다.**
   - 차단 중 만료 시각에 이른 `PENDING`·`RETRY_WAIT` 작업은 ADR-0002의 주기 sweep이 `EXPIRED`로 전이한다.
   - sweep은 차단기가 `open`이어도 멈추지 않는다.
7. **일부 수신자만 거부되면 `SENT`로 처리하고 재시도하지 않는다.**
   - 거부된 수신자와 응답을 `mail_attempts`에 기록한다.
   - 수락된 수신자에게 재시도로 중복 발송하는 것을 막기 위해서다.
   - 상태 조회와 `JOB_SENT` 이벤트(ADR-0006)에 `rejectedRecipients`를 포함한다.
   - 일부만 수락된 경우 `4xx`로 거부된 수신자는 재시도하지 않고 `rejectedRecipients`에 남는다.
   - 전원이 거부되면, 하나라도 `4xx`이면 `TRANSIENT`이고 모두 `5xx`이면 `PERMANENT`다.
8. **`Message-ID`는 작업 ID에서 유도한 고정값을 쓴다.**
   - 같은 작업의 재시도는 같은 `Message-ID`를 쓴다.
   - 도메인 부분은 발신 계정 도메인이다.
   - Gmail이 같은 `Message-ID`를 중복으로 버리는지는 확인하지 못했다. 중복 완화 수단이며 보장이 아니다.
9. **SMTP 라이브러리는 nodemailer이며, 단계는 라이브러리의 오류 정보로 판별한다.**
   - nodemailer를 쓰면 오류의 `command`, `responseCode`, `code`(예: `EAUTH`, `ECONNECTION`, `ETIMEDOUT`)를 쓸 수 있다고 알려져 있다.
   - 구현 중 nodemailer 10.6.1로 실측했다. 서버 응답 오류는 이 필드로 판별하고, 전송 계층 오류는 `command`만으로 판별할 수 없어 보완했다(구현 중 확정 1).
10. **호출처별 발송 할당은 발송 단계에 두고 2단계에서 구현한다.** 구현됨(2026-11-23): 구현 중 확정 7이 사용량 정의와 구현 세부를 정한다.
    - 호출처별 24시간 rolling 할당을 설정 항목으로 둔다. 기본값은 무제한이다.
    - 할당을 초과한 호출처의 작업은 점유 대상에서 빼고 시도 횟수를 쓰지 않는다.
    - 등록 단계에는 쿼터를 두지 않는다(ADR-0005 결정 5).

## 구현 중 확정 (2026-11-23)

1단계 구현 중 확정한 내용이다. 위 결정을 보완하거나 바꾼다. 충돌하면 이 절이 우선한다.

1. **nodemailer 오류 필드 실측과 단계 판별 보완(결정 9).**
   - 실측 환경: nodemailer 10.6.1, 로컬 smtp-server 3.21.7. 근거 테스트는 `test/smtp/nodemailer-errors.spec.ts`다. 실제 Gmail 서버 대상으로는 확인하지 않았다.
   - 서버 응답 오류는 추정대로다.
     - `code`는 `EENVELOPE`(`MAIL FROM`·`RCPT TO`·`DATA` 명령 응답), `EMESSAGE`(`DATA` 본문 응답), `EAUTH`(인증)다.
     - `command`는 실제 명령(`MAIL FROM`, `RCPT TO`, `DATA`, `AUTH PLAIN`), `responseCode`는 숫자, `response`는 응답 원문이다.
     - 수신자 전원 거부는 `rejectedErrors`에 수신자별 오류가 있다. 일부만 수락되면 오류 없이 결과 객체에 `accepted`·`rejected`·`rejectedErrors`가 온다.
   - 추정과 달랐던 부분이다.
     - 소켓 타임아웃(`ETIMEDOUT`), 연결 끊김(`ECONNECTION`), 인증서 검증 실패는 진행 중인 단계와 무관하게 `command`가 항상 `"CONN"`이다.
     - 그래서 `command`만 쓰면 `DATA` 단계 타임아웃(`TRANSIENT`)이 연결 단계 오류(계정 상태 오류)로 분류된다.
     - 연결 거부는 `code`가 `ESOCKET`이고 `originalCode`가 `ECONNREFUSED`다. 추정은 `ECONNECTION`이었다.
     - STARTTLS 거부는 `code`가 `ETLS`이고 `responseCode`가 500이다.
   - 보완: `StageTracker`(`src/smtp/sender.ts`)가 nodemailer의 SMTP 명령·응답 로그로 "응답을 기다리는 가장 오래된 명령"의 단계를 추적한다.
     - 전송 계층 오류에는 이 단계를 `command` 대신 쓴다. 서버 응답이 있는 오류는 `command`를 따른다.
     - 판별하지 못하면 연결(CONN)로 둔다. 계정 상태 오류가 되어 시도 횟수를 쓰지 않는 쪽이다.
     - 이 로그 훅은 단계 추적에만 쓰고 주소·본문·자격 증명을 보관하지 않는다.
2. **분류 표 보완(결정 3·4, `src/smtp/classify.ts`).** 규칙은 위에서 아래로 처음 맞는 것을 쓴다.
   - `550 5.7.1`을 응답 텍스트로 가른다.
     - 스팸 의심·정책 거부·`Message-ID`나 `From` 누락 텍스트는 메시지 오류 `PERMANENT`다.
     - relay 자격·구성 텍스트는 계정 오류다. 일일 한도 텍스트는 일일 한도, `rate limited`는 순간 한도다.
     - 구분할 수 없으면 계정 오류다(결정 4).
   - `450 4.2.1`이라도 "수신자가 너무 빨리 받고 있다"는 수신자 쪽 제한 텍스트는 메시지 오류 `TRANSIENT`다. 그 밖의 `450 4.2.1`과 `Peak SMTP relay limit`은 순간 한도다.
   - `421`은 결정 4의 `4.7.0`·`4.4.5` 외에 `4.7.x` 전체를 순간 한도로, 그 밖의 `421`을 일반 계정 오류로 둔다(추정).
   - `454`·`530`·`534`·`535`는 단계와 무관하게 계정 오류다. `538`·`432`는 RFC 기준의 추정이다.
   - `MAIL FROM`·`RCPT` 단계의 타임아웃·연결 끊김은 계정 오류, `DATA` 단계는 `TRANSIENT`다.
   - 규칙에 없는 응답은 `TRANSIENT`다. 시도 횟수와 만료 시각이 재시도를 제한한다.
   - Google 문서 기반 규칙은 2026-11-23에 가져온 페이지를 요약 도구로 읽어 정했다. 원문 전체와 대조하지 않았다.
   - 전원 거부(결정 7)에 계정 오류가 섞이면 계정 오류가 우선한다. ADR에 없던 규칙이다. 한도는 단계와 무관하게 계정 상태 오류이므로 `PERMANENT`로 확정하면 안 되기 때문이다. 사유가 여럿이면 대기가 긴 쪽(일일 한도, 순간 한도, 일반 순)을 쓴다.
3. **대표 작업 선택과 `account_trips`(결정 4·5).**
   - 대표 작업은 직전에 차단기를 연 작업을 제외하지 않고 후순위로 둔다(`mail_circuit_breaker.last_trip_job_id`). 제외하면 작업이 1건뿐인 큐가 멈추고, 그 작업의 `account_trips` 예외가 작동하지 않기 때문이다.
   - `account_trips`는 `MAIL FROM` 이후 단계의 계정 상태 오류가 그 작업 때문에 차단기를 `open`으로 바꾼 횟수다. 오류가 난 횟수가 아니다.
   - 3회 연 뒤 직전 계정 상태 오류와 응답(응답 코드와 enhanced status code)이 같은 오류가 오면, 4번째 오류에서 `FAILED`(`ACCOUNT_REPEATED`)로 전이한다. 이 시도도 시도 횟수에 넣지 않는다.
   - 응답이 직전과 다르면 `FAILED`로 승격하지 않는다. `account_trips`는 줄이지 않고 계속 센다.
   - 직전 응답은 `mail_jobs.last_account_response`에 `"코드 enhanced코드"` 문자열로 둔다.
4. **차단기 저장소 위치와 컬럼(결정 5).**
   - 저장소 코드는 `src/queue/circuit-breaker.ts`다. DB를 소유한 모듈에 둔다. 사유 분류는 `smtp` 모듈이 정해 큐에 넘긴다.
   - 추가한 컬럼: `probe_job_id`(대표 작업), `wait_seconds`(마지막 open 대기), `consecutive_failures`, `last_trip_job_id`, `last_trip_token`(전이 호출 식별).
   - 잠금 순서는 작업 행, 차단기 행이다. 점유 경로와 결과 기록 경로가 같은 순서를 써서 교착을 피한다.
   - SMTP 구성이 여럿일 때의 차단기 키 구성은 정하지 않았다. 1단계는 `breaker_key`가 `default`인 한 행이다.
5. **응답 텍스트 마스킹(미확정 해소, ADR-0003 미확정 포함).**
   - 분류는 원문으로 하고, 시도 기록과 결과에 담는 텍스트는 이메일 주소 형태를 `[address]`로 바꾸고 500자로 자른다(`sanitizeResponseText`, `src/smtp/sender.ts`).
   - 서버가 수신자 주소를 응답에 되풀이하는 경우(예: `550 5.1.1 <user@x> ...`)를 막기 위해서다.
   - `rejectedRecipients`의 `address`는 RQ-016이 요구하는 값이므로 가리지 않는다. 이벤트의 `failure_detail`에는 코드만 넣고 REST 응답에는 응답 텍스트를 싣지 않는다.
   - 한계: 주소 형태(`@` 포함)만 가린다. 서버가 사용자 이름만 되풀이하는 경우는 가리지 못한다(추정).
   - 검증: `test/worker/worker.integration-spec.ts`의 canary 테스트가 시도 기록과 로그에서 주소가 사라진 것을 확인한다.
6. **Mailo 내부 오류(독성 작업) 처리.**
   - 본문 복호화 실패, 본문·수신자·봉투 형식 오류 같은 Worker 내부 오류는 SMTP 단계가 없다. 같은 작업이 다시 실패할 가능성이 높아 최대 시도 횟수(기본 8)까지 재시도하지 않는다.
   - 1·2번째 시도는 `TRANSIENT`(단계 `WORKER`)로 시도 횟수에 넣고, `poisonMaxAttempts`(기본 3, 추정)번째 시도에서 `PERMANENT`로 `FAILED`가 된다.
   - 본문이 이미 삭제된 작업(`BODY_MISSING`)은 첫 시도에서 바로 `FAILED`다.
   - 내부 오류 결과에는 `internal` 표시를 붙인다. 큐는 이 결과로 차단기를 갱신하지 않는다. 계정 상태를 확인하지 못한 결과이므로, `half_open` 대표 작업이 내부 오류로 끝나도 차단기는 `half_open`과 대표 작업을 유지한다(`test/queue/circuit-breaker.integration-spec.ts`).
   - 한계: 대표 작업이 내부 오류로 끝나면 `probe_until`(작업 lease와 같은 값)이 지난 뒤에야 다른 인스턴스가 다시 대표 작업을 점유한다. 그동안 차단은 풀리지 않는다(코드 읽기 결과이며 시간 경과 시나리오는 테스트하지 않았다).

7. **호출처별 발송 할당 구현(결정 10, RQ-032, 2026-11-23).** 결정 문구는 바꾸지 않는다. 사용량 정의와 구현 세부를 확정한다. 코드는 `src/queue/claim.ts`(`planQuotas`), 설정은 `src/callers/registry.ts`(`sendQuota24h`)다.
   - 설정: 호출처 레지스트리의 `sendQuota24h`. 1~10000000의 정수이고 생략하거나 `null`이면 무제한이다. 0은 허용하지 않는다(발송 중지는 호출처를 빼서 표현한다). 레지스트리는 기동 때 한 번 읽으므로 변경은 재시작 뒤 반영된다.
   - **사용량 정의.** 사용량 = 최근 24시간(`finished_at > now() - interval '24 hours'`)의 "할당에 드는 시도" 수 + 현재 `SENDING`인 작업 수다. 할당에 드는 시도는 `mail_attempts`에서 `counted`이고 `stage`가 `WORKER`가 아닌 것이다. 따라서 `TRANSIENT`·`PERMANENT`·`LEASE_EXPIRED`와 `SENT` 시도는 들고, 계정 상태 오류(`ACCOUNT`, `counted = false`)와 Mailo 내부 오류(`stage = 'WORKER'`)는 들지 않는다.
   - 단위는 메시지 시도 수이고 수신자 수로 가중하지 않는다. 한 메시지의 수신자가 100명이어도 1이다.
   - 점유 전에 호출처마다 남은 건수(`할당 − 사용량`)를 정한다. 남은 건수가 0 이하인 호출처는 이번 점유에서 뺀다. 남은 건수가 있는 호출처는 그 건수까지만 점유하므로 한 번의 호출이 `limit`보다 적게 점유할 수 있다. `half_open` 대표 작업도 초과 호출처의 작업은 고르지 않는다.
   - 제외된 작업의 상태, 시도 횟수, `next_attempt_at`은 바뀌지 않는다. 할당이 풀리거나 만료 sweep이 처리할 때까지 그대로 둔다. 대기 중 `expires_at`에 이르면 `EXPIRED`다.
   - **경계 초과 0건.** 호출처별 `pg_try_advisory_xact_lock(7364222, hashtext(caller_id))`를 잡은 트랜잭션만 그 호출처의 사용량을 읽고 점유한다. 락은 커밋 때 풀린다. 못 잡은 인스턴스는 기다리지 않고 그 호출처를 이번 점유에서만 건너뛴다. 사용량 읽기부터 점유 커밋까지 호출처별로 한 인스턴스만 들어오므로 동시 점유로 인한 초과가 없다. 시도 수와 점유 수는 한 문장(한 스냅샷)에서 센다. 점유한 작업이 곧 `SENDING`으로 사용량에 든다.
   - **스키마.** `migrations/0002_caller_quota.sql`이 `mail_attempts.caller_id`(NULL 허용)를 추가하고 기존 행을 `mail_jobs`에서 채운다. 부분 인덱스 `mail_attempts_quota_idx (caller_id, finished_at) WHERE counted AND stage IS DISTINCT FROM 'WORKER'`와 `mail_jobs_sending_caller_idx (caller_id) WHERE status = 'SENDING'`를 둔다. 사용량 쿼리의 `WHERE`가 부분 인덱스 조건과 같아야 인덱스를 쓴다. 비용은 할당을 설정한 호출처 수와 그 호출처의 최근 시도 수(`LIMIT 할당`으로 자른다)에 비례하고 큐 길이에는 영향받지 않는다.
   - `caller_id` NULL을 허용하는 이유: 이 마이그레이션 전 버전의 인스턴스가 롤링 배포 중 `caller_id` 없이 쓴 행을 거부하지 않기 위해서다. 그런 행은 사용량에 잡히지 않는다(롤링 구간의 과소 계수).
   - **로그.** `caller_quota_exceeded`(warn, `callerId`, `limit`)는 호출처가 초과 상태가 될 때 한 번, `caller_quota_recovered`(info, `callerId`)는 풀릴 때 한 번 남는다. 폴링마다 반복하지 않는다. 다른 인스턴스가 점유 중이라 이번에 건너뛴 호출처는 초과로 기록하지 않는다.
   - 검증: `test/queue/caller-quota.integration-spec.ts` 12건(인스턴스 12개 동시 점유의 초과 0건 포함), `test/worker/worker-quota.integration-spec.ts` 3건, `test/callers/send-quota.spec.ts`. 한계: 실제 다중 프로세스·장시간 부하와 실제 Gmail 한도와의 관계는 확인하지 않았다. 호출처 할당의 합이 계정 한도를 넘지 않는다는 보장은 없다.

## 검토한 대안

| 대안                                       | 채택하지 않은 이유                                                           |
| ------------------------------------------ | ---------------------------------------------------------------------------- |
| ADR-0003의 `SYSTEM` 분류만 유지            | 연결 오류와 한도 초과를 막지 못한다. 매핑 표가 계정 상태 판정까지 맡게 된다  |
| 프로세스별 연속 오류 카운터                | 인스턴스 수만큼 잘못된 인증을 시도하고 해제 조건이 인스턴스마다 다르다       |
| 한도 초과를 작업 단위 `TRANSIENT`로 처리   | 한도가 풀릴 때까지 작업마다 시도를 소모해 큐 전체가 실패·만료된다            |

## 결과

- 계정 단위 장애로 큐 전체가 `FAILED`나 `EXPIRED`가 되는 경우가 줄어든다.
- 잘못된 인증으로 반복 접속해 계정이 잠기는 위험이 줄어든다. 이 위험은 추정이다.
- 차단기 상태 행과 상태 전이 로직이 추가된다.
- 매핑 표는 메시지 단계 코드에만 쓰므로 범위가 좁아진다.
- 일부 수신자 거부를 `SENT`로 처리하므로 `SENT`의 의미(RQ-016)에 "일부 수신자 거부 가능"을 추가해야 한다.
- 차단 시간이 길어지면 만료 시각이 지난 작업이 `EXPIRED`로 쌓인다.
- 이 ADR의 규칙은 로컬 SMTP 서버와 PostgreSQL 대상 테스트로 확인했다(결정 10은 구현 중 확정 7). 실제 Gmail 서버 대상 동작은 확인하지 않았다.
- 응답 코드·텍스트 분류 규칙 일부는 추정이다(구현 중 확정 2). Gmail 응답이 달라지면 매핑 표를 고친다.

## 미확정

- SMTP 구성이 여럿일 때 차단기 키 구성.
- 계정 전체의 발송 속도를 선제적으로 제한할지 여부.
- 응답 텍스트 패턴 목록의 실제 Gmail 응답 대조와 일일·순간 한도 외 유형의 재개 시각. 1단계는 구현 중 확정 2의 패턴과 사유별 초기값(연결·TLS·인증 1분)을 쓴다.
- 결정됨: 응답 텍스트에 수신자 주소가 들어갈 때의 마스킹은 구현 중 확정 5가 정했다.
